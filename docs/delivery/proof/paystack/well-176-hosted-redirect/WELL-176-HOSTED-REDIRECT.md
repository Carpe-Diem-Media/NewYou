## Hosted Redirect and Commerce lifecycle

1. **Purchase admitted → Initialize reserved.** NewYou authenticates and authorizes the payer for the same accepted purchase. Respect the governed unused-credit guard. Freeze price/version, component allocations, purchaser/recipient relationship, amount in ZAR cents, provider, integration and environment. Persist the opaque unique merchant reference and a single dispatch reservation. Serialize the admission under Commerce using an atomic change/constraint. Scope provider identity to provider/integration/environment. A second browser sees the same intent or a safe authorization failure. A different purchase key does not defeat the access/credit admission guard. After reserving, hold no database lock across the network. Only the winning sender may issue one `POST /transaction/initialize`. Disable client/proxy redirects and hidden retries. A crash even before actual send is uncertain without affirmative no-dispatch evidence.
2. **Initialize accepted → exact capability retained → 303.** Use Paystack's server REST contract with a restricted key, unique reference, authorized email, exact amount/currency, card-only channel for first proof and a fixed NewYou callback URL. On the first trusted boundary to receive the complete matching response, persist its original `authorization_url`, `access_code` and reference atomically before returning any participant response. Encrypt access to the capability and restrict its exposure and retention. Require success envelope, exact reference and strict approved URL syntax. Only serve the stored URL verbatim in a 303 to the payer's explicit CSRF-protected action. Do not take a client URL or derive a URL from reference/code. Use no-store and no-referrer and exclude capabilities, codes and URLs from analytics, traces, logs and support views. The proof accepts exact `https://checkout.paystack.com/<one opaque ASCII path token>` as a conservative candidate. The provider must confirm allowed production URL forms. A mismatched/partial response leaves the attempt fenced. [Paystack Initialize](https://paystack.com/docs/v2/api/transaction) · [Hosted redirect flow](https://paystack.com/docs/payments/accept-payments/)
3. **Response lost after retention → reconnect to original.** At sign-in, use the owning intent and recheck the current authorized payer and monetary state. Pending, locally suppressed, paid, review and no retained URL are different outcomes. Once provider semantics and EV-001B are approved, an eligible payer may explicitly reopen the stored URL. Preserve its exact bytes through restart, keep the same reference and grant no extra dispatch. Concurrent resume can present only this same capability. Rate-limit or single-flight presentation if needed, but a local lease cannot revoke a URL already shown to another tab. Require Paystack evidence for overlapping-use safety before enabling recovery broadly.
4. **Initialize accepted upstream but never durably retained → unresolved without capability.** Do not reconstruct URLs, replay Initialize or authorize another attempt. Use original-reference Verify and authenticated webhook evidence. Paystack publicly documents creation and status reads, and the reviewed Verify/Fetch/List schemas publish no supported capability reissue. Write-through receipt retention shrinks the interval in which a capability can be lost. It cannot recover bytes that never reached NewYou. Start bounded reconciliation with jitter/backoff and durable next-due state. Positive success can recover the paid right. A missing capability needed to pay requires one operator case and attributable provider resolution. A read miss is a point observation. [Transaction reference](https://paystack.com/docs/v2/api/transaction) · [Duplicate reference errors](https://paystack.com/docs/api/errors/transaction/)
5. **Return, webhook, or no signal → reconcile the same attempt.** Use the callback reference as an input to a known-intent lookup or verification trigger. Re-authorize the participant before showing details, and clear sensitive redirect parameters with a local redirect. Do not accept amount, entitlement, payer or success from browser data. Authenticated, privacy-bounded raw webhook ingress records a deduplicated receipt and recoverable work before acknowledgment. Paystack can repeat events. Check the applicable signing scheme before choosing the exact adapter. Scope event identity to integration/environment and use a proven event ID or canonical evidence identity, retaining independent payment-effect dedupe. A base poll/sweep and catch-up after outages ensure a missing browser, missing webhook, or lost job does not orphan the attempt. Verify independently with a restricted server key, no open URL construction. Handle late success after failure, unavailable Verify, 429, and duplicate or reordered delivery. [Verify a payment](https://paystack.com/docs/v2/payments/online/verify-payments) · [Webhook verification](https://paystack.com/docs/payments/webhooks/)
6. **Verified success → paid → idempotent entitlement.** Bind provider/integration/mode, original reference, lossless numeric transaction ID when known, exact amount/currency, and identity against the immutable receipt. Distinguish API envelope true from transaction success. Persist the financial application and durable consequence intent in one owning Commerce decision. Use Entitlements' owning interface keyed by obligation/component and governed recipient. Deduplicate execution and acknowledgment separately. Pending, stale failure and duplicate success cannot undo verified payment. A genuine reversal, chargeback or distinct excess collection adds evidence and starts its governed lifecycle, including source-scoped rights and DEC-314 correction. The first once-off slice needs a discoverable retry for a lost acknowledgment, with no lost consequence after review deadline.
7. **Pending, abandonment, decline, expiry, timeout or unknown remain unresolved unless provider finality is independently proven.** Stop re-presenting a capability when it is stale or its eligibility is unknown. Persist one operator case when bounded recovery exceeds its time budget. Keep a slower reconciliation backstop and an authorized status journey through the review. Never imply the buyer should pay again. Local or provider display expiry is not the same as financial finality. A future replacement must require provider-backed evidence of both irreversible old capability nonpayability and resolution of in-flight collection, an atomic paid-vs-replacement recheck, and one new reservation under the same intended obligation. Retain prior history and handle contradictory late collection by review/DEC-314. These predicates remain unimplemented and unverified for Paystack. [Timeout settings](https://paystack.com/docs/v2/api/integration) · [Paystack transaction errors](https://paystack.com/docs/api/errors/transaction/)

The engineering choices are short owned Ash actions, PostgreSQL identities/constraints, durable job/receipt work and an idempotent Entitlements consumer. Choose the existing NewYou stack. Avoid a separate payment engine, process authority, Redis or Store's web/domain layout.

## EV-001B and the smallest experiment

**Paystack supports Hosted Redirect. Its docs do not establish the identity of a fresh resumed hosted session or authorize replacement after expiry.** Exact URL, an actionable form, a callback, a timestamped log delta and two matching Verify responses still describe separate observations. The qualifying evidence must join the actual settled or pre-payment **resumed hosted session** to the original provider transaction. Reference matching alone has no session provenance.

**Smallest next authorization.** Approve sending the [identifier-free Paystack support draft](PAYSTACK-SUPPORT-DRAFT.md). Ask for the supported proof of retained URL → fresh hosted session → exact Verify ID, permitted pre-payment request inventory, and safe reopen/finality/reissue guarantees. Written contract or an approved read-only provider observation would avoid a payment test and constrain the executable prerequisite. If no authoritative pre-payment witness exists, separately assess an intentionally authorized, single card-only TEST settlement through the retained link as a stronger identity witness. It would need a proven fresh hosted interaction joined to the same transaction and evidence of no extra payable attempt. It would require a new Master Gate and owner decision, and falls outside the current zero-payment protocol. It would still leave expiry/overlap to their own cases.

**Conditional no-payment run after provider evidence and approval.**

- Use one independent synthetic card-only ZAR TEST intent and a one-shot isolated runner. Server lane at `https://api.paystack.co:443` permits one `POST /transaction/initialize` and at most two `GET /transaction/verify/{same-synthetic-reference}`, one before and one after the fresh navigation. One successful durably retained tuple, no reinitialization, retry, redirect, alternate endpoint, live key, real account setting change, card input or payment. Use the existing restricted TEST scope. Do not use the original unresolved attempt.
- Scope the participant response cut to independently observed after receipt commit. Reopen the authorized payer in a fresh isolated browser with the exact retained URL. Browser permits one `GET https://checkout.paystack.com/{exact-retained-token}` and exact pre-reviewed same-origin GET/HEAD resources. No stock wildcard allowlist. Use the certified ceilings of 60 requests, four seconds per intercepted request and ten seconds for navigation, or tighter approved limits. No navigation redirects, retries, socket bypass, new origin or POST. Actual asset allowlist awaits provider evidence. Enforce HTTP before upstream dispatch with an isolated browser/driver/controller, Chromium sandbox qualification, a default-deny broker or equivalent preventive control, independent receiver-side tests and cold browser/profile preflight. Workstation Chromium isolation from earlier synthetic work cannot be taken as this qualification.
- **PASS** requires exactly one Initialize and one effective reopening after the induced cut, no extra operation or payment, and a fresh, authentic provider-issued witness tying the recovered session and retained capability to the same exact lossless transaction ID as both authenticated Verify observations. Match integration, TEST mode, merchant reference, expected ZAR amount/currency and acceptable non-success states. A provider-issued witness needs an independently verified mechanism and provenance, for example a documented provider response to that one session tagged with the original identity. There is no such approved witness today. Sanitized evidence records baseline, cut, counters, versions, matching flags and scope. It excludes raw codes, IDs, URLs, secrets and customer data.
- **STOP** on a budget violation, ambiguous second payable attempt, unexpected or denied operation, inability to mediate, unknown origin or redirect, changed admission or identity, masked transport retry, or any payment indication. **INCONCLUSIVE** when the browser stays within guard but independent provider session linkage is missing. Leave EV-001B NOT_EXECUTED during this offline task. A future witnessed PASS only applies to that case and does not answer EV-001C, EV-009A/B, EV-050 actual-stack proof or OQ-004 as a whole.
