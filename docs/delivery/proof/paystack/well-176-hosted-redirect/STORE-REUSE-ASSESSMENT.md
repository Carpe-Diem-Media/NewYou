## Admission, price and provider capability

- **REUSE the checkout admission pattern.** Store retrieves/creates a checkout in a transaction with cart/order locks. Order creation upserts by `checkout_key` with no update fields. PostgreSQL enforces uniqueness. The checkout tests cover reentry for the same cart version and concurrency. NewYou should key admission to the same accepted Purchase Intent and separately enforce governed unused-credit admission across standalone and bundle purchases. A unique checkout key cannot distinguish two distinct commercial obligations or prevent a second admission under a different key. Keep payer and entitlement recipient distinct. - **REUSE the immutable snapshot pattern.** The writer reuses persisted lines and totals when already finalized. The migration enforces one line number per order. The finalize test covers snapshot creation once. Adapt the snapshot to NewYou's versioned price, currency, immutable component allocation and purchaser/recipient relationship. Exclude Store's cart, shipping, product holds and inventory actions. [Snapshot writer](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/lib/store/orders/snapshot_writer.ex#L30-L63) · [Snapshot migration](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/priv/repo/migrations/20260224140000_phase_09_immutable_snapshots.exs#L9-L34) · [Finalize test](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/test/store/checkout/domain_test.exs#L287)
- **COMPOSE a dedicated provider dispatch fence from Store's stronger claim pattern.** Store's ordinary payment path checks checkout actor, finalized totals and enabled provider, and creates/reuses the local intent. Its partial in-flight unique index only covers `submitted` and `requires_action`. The missing-provider-reference branch can refresh a pending setup and enter another provider request. Stripe receives the stable intent key as its idempotency key. This is not an irreversible dispatch claim for Paystack. Store's recurring collection is stronger: a locked exact-epoch claim binds its intent and reserves the outcome before dispatch. Tests assert the durable request reference and one winner on the epoch under concurrency. Borrow the claim principle and database uniqueness in a Commerce-owned Ash boundary. Use a much smaller one-off record and leave renewal, stored card, retry/replay, epoch and inventory semantics behind unless they independently fit. - **EXTEND provider reference separation and evidence.** Store records reference kind, transaction ID, amount, currency, environment, times and outcome. `PaymentAttempt` has durable event/attempt identities and system-only recording, while `PaymentIntent` has nullable unique provider payment, session and request IDs. Store also persists the provider checkout URL. For NewYou, separate the pre-dispatch Provider Attempt from immutable observation rows, scope identity to provider/integration/environment, record lossless ID when first authenticated, and expose the encrypted URL only through the authorized redirect action. Store's resource metadata marks its URL and client-secret fields public. Review fields and telemetry at the NewYou boundary instead of borrowing visibility or a generic admin override. - **INTRODUCE the Paystack-specific Hosted Redirect adapter and proof.** Although Store advertises one-time checkout in the module's capability map, its Paystack `create_intent`, payment observation and webhook verification/normalization are unimplemented. It denies safe same-request replay in the capability map. Store's verified Stripe adapter behavior cannot certify Paystack. ## Money, evidence and rights

- **REUSE the verified correction and application pattern.** Older CER evidence flagged a failed terminal state blocking late success. Current Store permits system-only `correct_to_succeeded` and the application code invokes it only with verified correction. A source regression deliberately leaves a failed intent unchanged during observation, then applies it as paid; another races duplicate observations. `PaymentApplication` has a unique application key and applies under Order/PaymentIntent locks with revalidation in one transaction. Adapt to owning Commerce actions and one authorized effect per accepted obligation. Deduplicate repeat evidence independently of actual distinct collections and their DEC-314 excess remedy. [Transition and guard](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/lib/store/payments/interlocks.ex#L1847-L1865) · [Apply once](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/lib/store/payments/interlocks.ex#L1700-L1750) · [Payment application constraint](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/priv/repo/migrations/20260225190004_phase_14_checkout_interlocks.exs#L74-L117) · [Late success test](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/test/store/workers/process_webhook_receipt_worker_test.exs#L287-L336)
- **EXTEND webhook receipt and reconciliation.** Store captures raw bytes, verifies through an adapter, persists digests and provider-event evidence, deduplicates receipts and queues processing. Reuse the boundary with Paystack's applicable signature scheme, event identity and privacy limits. A duplicate receipt skips enqueue and enqueue is separate from receipt persistence. Prove durable work recovery or transactional enqueue on lost acknowledgement/job, plus a sweep over unresolved references. Never make receipt dedupe a substitute for payment application dedupe. Browser return remains read-only evidence and an optional reconciliation trigger, under NewYou authorization. [Webhook ingress and queue](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/lib/store_web/controllers/webhook_controller.ex#L116-L175) · [Webhook dedupe migration](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/priv/repo/migrations/20260222162948_phase_05_uniqueness.exs#L11-L37) · [Receipt worker](https://github.com/Carpe-Diem-Media/Store_Blueprint_Hardening/blob/949821ac589addb6e595f6333370ed65cf8d5ef7/lib/store/workers/process_webhook_receipt_worker.ex#L9-L29)
- **COMPOSE durable, source-aware consequence convergence.** Store's post-payment notifications/enqueues occur outside the payment transaction. The newer subscription path has a durable `AccessEffect` keyed by subscription/source version, a bounded recovery worker, exact-source grant identity and tests for stale targets and rollback/recovery of failed application. This materially hardens the old CER convergence concern for the inspected source. It does not certify once-off NewYou outcomes, every lost-dispatch crash window or recipient/component/credit semantics. Use a durable Commerce consequence and idempotent owner-facing Entitlements application with a repair selector. A source-keyed external command plus acknowledgment recovery can be enough for the first one-off slice. Add versioned target fencing when required by governed revocation or multi-source semantics. ## Carry-forward boundaries

The older CER reuse assessment was based on Store main `56f06d0` and a hardened branch `54871ef`. Explicit failed-to-succeeded correction is **resolved in Store source** for the inspected verified flow. Recurring attempt admission and Subscription-to-Entitlements target convergence are **materially hardened in source** with scoped regression coverage. One-off unresolved Paystack dispatch, capability/session identity, payment replacement, new purchaser/grantee semantics and the exact NewYou once-off repair path **remain unverified or require adaptation**. The broader recurring lifecycle findings in CER were outside this FP-002 audit and stay unverified here. [Older CER findings](https://github.com/Carpe-Diem-Media/NewYou/blob/e7fc58167223be433d9ccc9d61d3aaeb2090a10c/docs/delivery/jit/commerce_entitlements/NEWYOU_CER_EVIDENCE_INDEX_WORKING_v0.2.1.md#8-store-reuse-evidence)

Both repos pin Ash 3.37.2, AshPostgres 2.15.2, Ecto SQL 3.14.0 and Postgrex 0.22.4. Store/NewYou differ in Ash State Machine 0.2.13/0.3.0, Phoenix 1.8.13/1.8.17, Oban 2.24.1/2.24.2 and Req 0.7.4/0.7.5. Store also pins Redix 1.8.2. Treat the source as patterns and proof cases. Use NewYou's installed framework, PostgreSQL constraints and durable job facilities. Reject wholesale Store imports, Store Domain ownership, Redis authority and Store's subscriptions, inventory, shipping and storefront behavior.
