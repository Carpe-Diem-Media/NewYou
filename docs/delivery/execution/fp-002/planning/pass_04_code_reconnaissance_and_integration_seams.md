### 4.4 Specific failure/race hotspots the agent must investigate before deciding JIT implementation

1. **Cross-transaction test realism.** ExUnit SQL Sandbox ownership can accidentally cause both concurrent writers to share one transaction. Prove two independent PostgreSQL connections/transactions; coordinate a real overlap and assert durable counts. Review existing concurrency test helpers, lock timeout and DB connection budget; do not assert a race from sequential calls.
2. **Commit boundary.** A Commerce verified payment and durable grant obligation must survive/rollback atomically. If code writes a payment then schedules an in-memory callback as the only consequence, it violates 7C. Do not wrap the *foreign Entitlements grant* in a parallel direct Repo/Ecto.Multi business write.
3. **Evidence trust.** TEST-only producer must be compiled only in test and have no production-reachable alternate path. Ordinary Ash public inputs, browser query parameters, request headers, generic provider payloads or test flags must not pass qualification without source-authenticated authority.
4. **Uniqueness under contention.** Ash application-level lookup followed by insert can race; DB integrity must make a second payment/consequence/right impossible. Pick the minimum unique/atomic mechanism proven by actual constraints and tests; don't hard-code a table plan before reconnaissance.
5. **Crash/reconciliation.** A job can finish/fail/expire without settling the durable business consequence. Use persistent source conditions for rediscovery and a fresh process/BEAM replay; instrument unresolved work without turning telemetry into authority.
6. **Identity new-Domain review.** Updating `:ash_domains` alone makes Identity reconciliation unavailable by design. Prove both existing positive cases and new review conflict/staleness. Don't broaden Identity's jurisdiction to update Commerce/Entitlements balances or rights.
7. **Historical/retention & privacy.** Right creation must not make deleted participant access reappear later; source history remains private. P1 only proves its directly scoped current-authority checks; future E2/Privacy interactions require own tests.
8. **Schema evolution and launch flags.** Verify migration direction, database and backwards-compatible code deployment for new Domains. No release or provider feature enabled by this P1 proof.
