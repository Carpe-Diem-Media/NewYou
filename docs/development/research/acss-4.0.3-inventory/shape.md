# Automatic.css 4.0.3 shape inventory

Research baseline: NewYou `4967b498d7413b7530303a64b4027e139e0b6d46`.
Reference package: supplied Automatic.css 4.0.3 archive, SHA-256 `17ee65acfd7e045e73b68f2373a2e4fba5e46ab3fd22ec5cc451472a7f5d63b5`. The package was inspected as source only. It was not executed or compiled.

This inventory records reusable mechanisms and their limits. It does not approve new design values, shadow styles, or page treatments. Frontend experience authority §8.1 treats Automatic.css as research, requires a lean native-variable system, and bars a Sass dependency added to imitate it. Existing DESIGN.md shape and elevation rules remain governing.

## Inputs and gates

### Shadows

Automatic.css separates three value types. Box-shadow settings are comma-separated shadow layers with x/y offsets, blur, spread, and color. The first three defaults contain multiple layers and HSL black with opacity from 0.02 to 0.105. Slots four and five default to null. Text-shadow defaults are single offset/blur/color values with alpha 0.2, 0.3, and 0.4; slots four and five are null. Drop-shadow defaults are filter-function arguments with alpha 0.15, 0.2, and 0.25; slots four and five are null. The variables and their units are in `assets/scss/modules/shadows/_box-shadow-vars.scss:1-26`, `assets/scss/modules/shadows/_text-shadow-vars.scss:1-13`, and `assets/scss/modules/shadows/_drop-shadow-vars.scss:1-13`.

Each token family has its own variable-output option, defaulting to `on`. The token files emit slots one through three unconditionally and slots four and five only when their configured values are non-null. Drop-shadow tokens wrap each configured argument in `drop-shadow(...)`; box and text values are emitted as supplied. See `assets/scss/modules/shadows/_box-shadow-tokens.scss:1-14`, `assets/scss/modules/shadows/_text-shadow-tokens.scss:1-14`, and `assets/scss/modules/shadows/_drop-shadow-tokens.scss:1-14`.

The cheatsheet advertises box-shadow utility names `box-shadow--1` through `box-shadow--5`, but its condition names a separate `option-box-shadows` setting. Its source is `assets/scss/modules/shadows/` file `_cheatsheet.json:1-26`. The inspected SCSS files define token output, not the corresponding utility selectors; therefore the cheatsheet is not proof that those declarations are emitted by the inspected source path. The PHP class registry also translates legacy modifier aliases `m`/`md` to slot 1, `l`/`lg` to slot 2, and `xl` to slot 3, then substitutes configured database names. An empty name suppresses the alias. See `classes/Model/Config/Framework.php:196-218` and `classes/Model/Config/Framework.php:243-272`. No equivalent text-shadow or drop-shadow utility declaration was found in the inspected SCSS/PHP paths.

Box shadow and drop shadow are not interchangeable. `box-shadow` paints the element's rectangular box and supports inset and spread values. CSS `drop-shadow()` filters the rendered alpha silhouette, so transparent image edges affect its shape; it has no spread or inset argument. Text shadow paints glyph silhouettes. These distinctions are inherent in the emitted property/function types. The vendor defaults are examples, not suitable NewYou defaults.

### Radius

The radius module takes a base length and a dimensionless scale factor. Defaults are `1rem` and `1.5`. It derives `s = base / scale`, `xs = s / scale`, `m = base`, `l = base × scale`, `xl = l × scale`, and `xxl = xl × scale`. At a 16px root, the explicit mapping is xs=7.11px, s=10.67px, m=16px, l=24px, xl=36px and xxl=54px. Units remain lengths because the factor has no unit. The formulas are in `assets/scss/modules/borders/_vars.scss:26-40` and the grouping in `assets/scss/modules/borders/_maps.scss:1-15`.

The radius-variable option defaults on and emits `--radius` and the non-size values (50%, 50vw, and 0). A separate size option defaults off. When enabled it emits all six scale sizes. When disabled it aliases only `--radius-m` to `--radius`. The `option-rounded` class gate and `option-radius-sizes` gate control generated class selectors independently of token output. `assets/scss/modules/borders/_tokens.scss:1-28` and `assets/scss/modules/borders/_classes.scss:27-55` show the two gates. The class cheatsheet lists `xs`, `s`, `m`, `l`, `xl`, `xxl`, `50`, `circle`, and `none` under its rounded option in `assets/scss/modules/borders/radius/` file `_cheatsheet.json:1-34`.

Automatic radius is a separately gated selector rule. With `$option-auto-radius: on` and a non-null `$auto-radius-selectors`, the source emits `:where(<configured selectors>) { border-radius: var(--radius); }`. The option defaults on, but the selector list defaults null, so the rule emits nothing until configured. `:where()` contributes zero specificity; a later or more specific component rule can override it. The input and output are in `assets/scss/modules/borders/_vars.scss:38-40` and `assets/scss/modules/borders/_auto-radius.scss:1-5`. Treating arbitrary tags or broad classes as auto-radius targets can change controls, media, and nested surfaces. Its low specificity does not make that broad visual effect safe.

### Concentric and inverted radii

The card mixin supports two mutually selected concentric modes. Standard mode computes outer card radius as `radius + card padding`, so the content edge can retain the chosen radius after padding. Reverse mode computes media radius as `max(card-min-radius, radius - card padding)`. The floor prevents negative or too-small media radii, but the formula assumes compatible length inputs; percentages, `auto`, or inconsistent local overrides need explicit validation. The option defaults `off`, card padding defaults to `var(--space-m)`, card radius defaults to `1rem`, and the minimum defaults to `4px`. See `assets/scss/modules/cards/_vars.scss:24-32` and `assets/scss/modules/cards/_mixins.scss:1-7`.

When enabled, the card mixin assigns the derived card/media variables and applies radii to its card and media descendants. The media selector excludes wrapper classes and also sets aspect ratio, clipping, and full inline size. It can affect nested component structures because it targets descendants by a class substring. `assets/scss/modules/cards/_mixins.scss:27-55` contains that behavior. The selector list for cards defaults to `.card`; the card feature defaults on. See `assets/scss/modules/cards/_vars.scss:1-11` and `assets/scss/modules/cards/_classes.scss:1-11`.

The inverted-radius framework is a separate compositional device. It draws up to two corner cutouts with `::before` and `::after`, selected by `data-inverted-radius-{1,2}-position` and `data-inverted-radius-{1,2}-slice`. It uses absolute positioning by default, a radius-sized square, a box shadow matching the background, and z-index/isolation. Positions include internal and outside placements. It is not a negative radius token or a general card/media radius scale. The framework gate defaults on in `assets/scss/modules/borders/inverted-radius/_vars.scss:1`; source mechanics appear in `assets/scss/modules/borders/inverted-radius/_utilities.scss:1-41` and `assets/scss/modules/borders/inverted-radius/_utilities.scss:143-201`. This structure requires dedicated clipping, stacking, and background proofs before use.

## Relationships

The box-shadow scale is a list of hand-configurable layered values, not a mathematical elevation scale. Names do not guarantee monotonic visual elevation; configured offsets, blur, spread, alpha, and color determine the appearance. Drop-shadow and text-shadow are separate output families with separate inputs and property semantics. Keep CSS stacking order (`z-index`) separate from visual elevation roles. A shadow can suggest depth without changing stacking order, and z-index can reorder content without drawing a shadow. Automatic.css declares a distinct z-index module (`assets/scss/modules/z-index/` file `_cheatsheet.json:1-19`); do not use either mechanism as a substitute for the other.

The radius scale is geometric and easy to calculate, but its default values do not match NewYou's approved discrete scale. Its 16px middle value and 24px large value coincide with existing tiers at the current root size, while 7.11px, 10.67px, 36px, and 54px do not. It cannot be adopted wholesale without changing the approved shapes.

Concentric radii are arithmetic relationships between outer radius, padding, and inner media radius. They are useful only when the relationship is intended by the component and the inputs share compatible length semantics. Inverted-radius cutouts are a different visual technique with pseudo-elements and stacking effects. Neither relationship authorizes rounded media or clipped corners on a currently flat/approved composition.

## Emitted tokens/selectors

Shadow token names are `--box-shadow-{name}`, `--text-shadow-{name}`, and `--drop-shadow-{name}` at `:root`. Their output is conditional by family option and configured fourth/fifth values. The cheatsheet lists box-shadow classes, but the inspected source did not locate declarations for those utility selectors. Treat box utility generation and all text/drop utility generation as unverified until a future proof finds and checks their actual output path.

Radius token output is at `:root`: `--radius`, `--radius-50`, `--radius-circle`, and `--radius-none` under the default radius-variable gate. Size tokens appear only with the size option; otherwise only `--radius-m` aliases the base. The class output uses `.radius`, `.radius--50`, `.radius--circle`, `.radius--none`, and optional `.radius--xs/s/m/l/xl/xxl`, controlled by the class gates. Automatic radius emits the configured `:where(...)` selector only when its selector list is supplied.

Card output is a configurable selector, `.card` by default, that receives layout, background, border, padding, typography, media, avatar, icon, link/button, and optional shadow styles. Its use extends well beyond radius. It is not a narrowly scoped radius helper. Inverted radius emits attribute selectors and pseudo-elements. These generated selectors should not be introduced globally as a side effect of adopting tokens.

## Dependencies/scope

The vendor project uses SCSS variables, maps, imports, and mixins to produce the described output. NewYou authority explicitly says not to add Sass to imitate this system. A NewYou implementation should express only the accepted relationships in its native CSS/Tailwind build and preserve its existing component APIs. Do not copy vendor code or turn utility-class availability into approval for new design values.

Shadow tokens can be adapted to the existing lighting role tokens only after review of the current role and consumer. NewYou already has `--shadow-flat`, `--shadow-ink`, `--shadow-strength`, `--shadow-control`, `--shadow-raised`, inset edge shadows, and action-state shadows. It has conditional surface/edge/shadow derivations, solid fallback values, and an action shine height. See `assets/css/design-tokens.css:121-140`, `assets/css/design-tokens.css:175-198`, and `assets/css/design-tokens.css:225-244`. These are semantic lighting relationships, not a generic five-tier box-shadow scale. Preserve the flat default, the opt-in lighting treatment, and the existing shine rule.

A future radius seam is the current root token set plus the design aliases, with semantic component classes consuming approved roles. Keep global root editing and component-local token scope consistent with the current design token contract. Do not add auto-radius selectors across controls or all cards. If a real repeated component relationship needs concentric radii, derive it locally from that component's radius and padding and prove it at its existing media/container states. Do not enable the vendor card recipe, its defaults, or inverted-radius utilities globally.

## Decision and implementation contract

**Shadows: adapt.** Keep NewYou's existing semantic shadow and edge roles. Do not import the vendor's sample values or create box/text/drop shadow utilities as a bundle. If a later implementation needs another shadow, make it a role required by an approved component/state, derive it from the existing lighting inputs where possible, preserve flat defaults and shine, and add an explicit rendered proof for default, opt-in, hover/pressed, disabled, forced-colour, and relevant surface contrast. Box shadow is appropriate for a rectangular component treatment; filter drop-shadow is appropriate only when the visible alpha silhouette is the intended shape; text shadow requires its own text-legibility approval. Do not call any of these "elevation" without defining the visual role. Proof IDs: `SHAPE-SHADOW-ROLE`, `SHAPE-SHADOW-SILHOUETTE`, `SHAPE-SHADOW-STATE`, `SHAPE-SHADOW-FALLBACK`.

**Radius: adapt.** Retain NewYou's approved five token values and component-owned shape roles. The reusable idea is a compact named scale and local derivation where repeated geometry requires it, not the vendor's default geometric output. Do not enable broad selector-driven auto-radius or introduce every vendor utility class. A future auto-radius rule must name a small allow-listed set of semantic targets and prove precedence, nested media, controls, focus rings, and 320px/resized behavior. A future concentric rule must state whether the outer radius is added to padding or subtracted from it, constrain all inputs to compatible lengths, and clamp the reverse result at an approved minimum. Defer inverted-radius cutouts unless an approved composition calls for the effect and separate pseudo-element/stacking proofs pass. Proof IDs: `SHAPE-RADIUS-SCALE`, `SHAPE-RADIUS-AUTO-SCOPE`, `SHAPE-RADIUS-CONCENTRIC`, `SHAPE-RADIUS-INVERTED`.

The inspected source paths also do not establish text-shadow/drop-shadow utility classes. No vendor code was run, and this inventory contains no browser rendering of its output. Existing design-token, lighting, and Hallmark evidence belongs to the recorded NewYou implementation baseline and does not prove any proposed adoption. ## Public recipe and framework distinction

The current public [border-radius recipe](https://docs.automaticcss.com/recipes/border-radius-recipes) describes adding half the padding to an inner radius. The inspected 4.0.3 card framework adds the full padding in standard mode. These are different recipes with different geometric intent. Do not substitute the public recipe for the archive formula or treat either as the approved NewYou relationship. A future component must state its actual outer border edge, inner padding edge, border width and media edge before choosing a formula. The simple subtraction identity does not account for every border-box or asymmetric-padding arrangement.
