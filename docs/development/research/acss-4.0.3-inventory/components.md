Research baseline: NewYou `4967b498d7413b7530303a64b4027e139e0b6d46`. Vendor evidence comes from the supplied `automatic.css-4.0.3.zip`, SHA-256 `17ee65acfd7e045e73b68f2373a2e4fba5e46ab3fd22ec5cc451472a7f5d63b5`. The archive was inspected without running the plugin or installing dependencies.

NewYou authority: `docs/governance/supporting/FRONTEND_EXPERIENCE_SYSTEM_v1.0.1.md` §8.1 calls for lean native-variable tokens and says Automatic.css is inspiration, not a runtime dependency; no Sass/SCSS should be added to imitate it. §8.2 calls for meaningful card grouping and one icon language. §8.4 requires real reuse and understood states/accessibility before a reusable pattern enters the system. ## Inputs and gates

**Icons.** The feature gate is `$option-icons` (default `on`); `$icon-data-attribute` defaults to `data-icon`. General defaults are scheme `inherit`, style `plain`, size from the medium size input (unset by default), padding `.35em`, and radius from the shared radius token. Color, hover color, background, border and shadow are nullable. The size map accepts `xs`, `s`, `m`, `l`, `xl` and `2xl`; individual size and padding values are nullable and only emit tokens when set. List icons have a `1em` size default, optional gap and offsets, and boxed list treatment is off by default. See `assets/scss/modules/icons/_vars.scss:3-6`, `32-73`, `75-93`.

**Cards.** `$option-cards` defaults on and `$card-selectors` defaults to null, then source prepends `.card, ` to its interpolated value. A configured selector can follow `.card`; the unconfigured trailing-comma case still needs compiler/output proof. Grid layout is off, so cards use flex. The default color scheme is light. Inputs cover background, heading/body/link colors, link hover, nested button style, avatar border, card border and shadow; padding/gap; radius and concentric-radius mode; heading/body/button typography; icon size and optional boxed icon treatment; avatar dimensions/radius/border/aspect; and media radius/aspect/object-fit. Several defaults derive from shared space, content-gap, text, icon, border, radius and color variables. See `assets/scss/modules/cards/_vars.scss:1-59`, `61-99`.

**Default and null behavior.** For icons, `$icon-size` resolves to `$icon-size-m`, which is null by default; `$icon-padding` is `.35em`; radius references `--radius`; border width and border style are both `0`; list icon size is `1em`; boxed list icons are off. Color, background, hover, shadow, six size/padding entries, list gap and offsets default null. The token loop omits nulls, but emits non-null values including zero, so `--icon-border-style: 0` is part of the declared defaults. In boxed styling, mixin fallbacks are padding `12px`, border width `0`, border style `solid`, radius shared `--radius`, background `--neutral-ultra-light`, and transparent border. `data-icon-size` supplies its value by selecting a size token, not a literal arbitrary size. See `assets/scss/modules/icons/_vars.scss:8-51`, `_mixins.scss:59-66`, `_classes.scss:6-23`.

For cards, enabled token declarations resolve to these finite keys: `--card-padding`, `--card-gap`, `--card-border-width`, `--card-border-style`, `--card-border-color`, `--card-display`, `--card-radius`, `--card-min-radius`, `--card-heading-size`, `--card-text-size`, `--card-button-font-size`, `--card-icon-size`, `--card-icon-padding`, `--card-icon-border-width`, `--card-icon-border-style`, `--card-icon-radius`, `--card-icon-background`, `--card-icon-color`, `--card-icon-border-color`, `--card-line-height`, `--card-avatar-radius`, `--card-avatar-border-width`, `--card-avatar-border-style`, `--card-avatar-size`, `--card-avatar-aspect-ratio`, `--card-media-radius`, `--card-media-aspect-ratio`, `--card-media-object-fit`, `--card-background`, `--card-heading-color`, `--card-text-color`, `--card-link-color`, `--card-link-color-hover`, `--card-button-style`, `--card-avatar-border-color`, and `--card-shadow`. The output loop omits null values. With current defaults, the omitted entries are heading color, link and link-hover color, button style, avatar border color/width/style, card border color, card shadow, and media aspect/object-fit. The `$card-icon-radius` input is declared twice with `!default`, first as null and then as `var(--icon-radius, var(--radius))`. This is a repeated input declaration, not a duplicate map key. Standard Sass applies a default when an earlier value is null, so the later declaration supplies the fallback unless prior configuration has a non-null value. See [Sass default-value semantics](https://sass-lang.com/documentation/variables/#default-values); actual configured plugin output remains unobserved. Other defaults include padding `var(--space-m)`, gap `calc(var(--content-gap) / 2)`, border width/style shared variables, radius `1rem`, minimum radius `4px`, heading `var(--h3)`, body `1em`, button font `var(--text-s)`, icon `48px`, line-height `1.4`, avatar size `98px`, square aspect ratio, `50vw` radius, and media radius `var(--radius)`. The null media aspect/object-fit tokens fall back to `16/9` and `fill` in the mixin. Flex display, clipped overflow, and color/layout rules are mixin behavior, not additional token keys. See `assets/scss/modules/cards/_vars.scss:9-59`, `61-99`, and `_mixins.scss:18-74`.

**Data attributes.** These are CSS selectors and style inputs in the reviewed component modules, not a universal attribute protocol. The icon module styles its configured base attribute (`data-icon` by default), `data-icon-size`, `data-icon-style`, `data-icon-list`, and `data-icon-hover`. Card rules accept class-based card targets, recognize a `__media`/`__avatar` naming convention, and look for descendant `[data-icon]`. Attributes elsewhere in the plugin have their own module-specific meaning. Do not infer that every `data-*` value is a visual API or that attributes imply JavaScript behavior.

## Relationships

The icon mixin accepts SVG, `i`, or anchor elements as visual icon hosts, sets sizing/alignment/overflow/transition and color, then styles `i::before` for font glyphs. It does not supply icon artwork. Hover values propagate from a hovered linked icon, a hovered link ancestor, a `[data-icon-hover]` region, or an anchor/button containing a direct SVG or `i`. The list pattern applies flex-column gap to the list container, sizes child SVG/`i`, and changes icon color/background on link hover. The style aliases `icon--boxed`/`data-icon-style="boxed"` and `icon--plain`/`data-icon-style="plain"`; size classes and `data-icon-size` set per-size variables. See `assets/scss/modules/icons/_mixins.scss:1-66` and `_classes.scss:1-51`.

The card mixin sets the outer layout, clipping, color scheme, border, spacing, background, text color and line-height. It assigns aspect ratio, object fit and full inline size to named media descendants; avatar selectors get their own size, ratio, crop and optional border. Headings use card heading tokens. Links inside cards inherit card link colors, with headings, button-like classes and icon hooks excluded. Descendant `[data-icon]` receives card icon sizing/color and optional boxed styles. Descendant `.btn--*` controls receive card button sizing and the shared button mixin. The stylesheet therefore couples cards to typography, media, avatar, icon and button systems. See `assets/scss/modules/cards/_mixins.scss:18-89`, `91-110`.

## Declared tokens/selectors

With its feature gate enabled, the icon token loop declares root custom properties for non-null style-map entries and non-null entries in the icon-size/padding maps. Source declares a base `[data-icon]` selector, size class/attribute pairs, boxed/plain class/attribute pairs, list rules and contextual hover rules. It does not emit glyphs or choose a vendor icon set. The supplied archive contains no precompiled ACSS framework CSS, so these are source-level output declarations, not observed runtime CSS. See `assets/scss/modules/icons/_tokens.scss:1-23` and `_classes.scss:1-51`.

Cards declare non-null values from the card style map as root `--card-*` properties. The class source targets configured selectors (initially `.card`), applies the card mixin, and sets light/dark `color-scheme` from matching class substrings. A consumer can add custom selectors, but this broad output is not equivalent to an explicit semantic component API. As above, the package lacks precompiled ACSS framework CSS; the source establishes intended output, not a runtime observation. See `assets/scss/modules/cards/_tokens.scss:1-10`, `_classes.scss:1-11`, and `_vars.scss:1-7`.

The declared icon selector value catalog is `data-icon-size="xs|s|m|l|xl|2xl"` and `data-icon-style="boxed|plain"`, plus attribute-presence selectors `[data-icon]`, `[data-icon-list]`, and `[data-icon-hover]`. Classes mirror the size and style variants; `icon-list` mirrors `data-icon-list`. These are finite size/style choices in this module, not a general component-state vocabulary. Card source has no card data-attribute variant selector; its initial target is `.card`, and its light/dark color-scheme behavior keys off class substrings `--light`/`--dark`.

Other data-attribute families found during the bounded scan have separate roles. The inverted-radius feature declares `data-inverted-radius-1-position` and `-2-position` with 16 values per attribute, covering four corners and outside-edge permutations, and `data-inverted-radius-1-slice`/`-2-slice` with four corner values each. They control pseudo-element placement, slices and shadows and depend on `--radius`; this is a specialized visual construction, so defer it. Layout and editor integrations include `data-etch-element="flex-div"` for an optional Etch adapter and `data-sticky-header="0"` as an exclusion input to automatic page offset. These are platform/configuration hooks, not general NewYou layout API. Color-scheme behavior in the card module uses class names, not data attributes. NewYou's `data-theme` is a site theme state observed by its design-system JS hook, a different contract from ACSS card class matching. None of these observations makes all `data-*` attributes a universal visual API. See `assets/scss/modules/borders/inverted-radius/_utilities.scss:1-4`, `44-140`, `144-201`; `assets/scss/modules/spacing/gap/_auto-gap.scss:16-31`; `assets/scss/modules/offset-content/_offset-content.scss:1-18`; and `assets/scss/modules/cards/_classes.scss:4-8`.

## Dependencies and scope

`automatic-imports.scss` imports card variables and mixins early, then icon variables, shared button maps and global helper/mixin infrastructure. The regular build entry imports tokens and feature output in layers; card classes and icon classes have separate feature layers. The card mixin calls shared button and icon-boxing mixins, so cards are not standalone. See `assets/scss/automatic-imports.scss:16-41`, `65-95`; `assets/scss/automatic.scss:1-30`.

The evidence examined here is SCSS configuration and intended CSS output. The icon module references SVG/i/font glyph markup supplied by its host. No component-specific JavaScript bootstrap is evident in these module files. ACSS also contains unrelated `data-*` selectors for other modules; each must be traced to its own inputs before use. Nothing here justifies adding a generic JS interpreter for attributes.

## NewYou comparison

**Icons: partial.** NewYou has a `<.icon>` Heroicons wrapper in `core_components.ex`, backed by the Heroicons dependency and Tailwind's `assets/vendor/heroicons.js` build plugin. It renders a named icon span with utility classes; it selects artwork and size/color utilities rather than implementing ACSS-style boxed/plain icon tokens, icon list behavior or hover propagation. Heroicons is an asset library and wrapper, not an icon styling framework. Current icon usage is scattered across components, so an opt-in semantic presentation helper may be useful only where repeated use is demonstrated. Evidence: `lib/new_you_web/components/core_components.ex:428-450`.

**Cards: partial.** `NewYouWeb.Components.Design.Card.design_card/1` provides a noninteractive semantic `<article>`, flat/raised variants, token utility composition, and rejects caller-owned class/variant overrides. It delegates actions to native links/buttons. It does not expose media/avatar/icon subcontracts or ACSS's configurable descendant styling. Existing `.card` use in layouts is legacy DaisyUI styling, not proof that every panel belongs in the design card API. Focused tests already cover raised and flat defaults, native metadata, caller class/variant rejection and unsupported variants in `test/new_you_web/design_system_infrastructure_test.exs:87-190`; no duplicate card-variant test is needed. Remaining proof is about any future media/avatar or nested icon contract and its responsive/accessibility behavior. Evidence: `lib/new_you_web/components/design/card.ex:1-36`, `assets/css/design-components.css:61-85`.

**Buttons and tokens: partial/implemented.** Shared design buttons own `data-variant` and `data-treatment`, preserve unrelated HTML/ARIA/LiveView attributes, and use native disabled state. Design tokens and component CSS provide semantic roles and opt-in lighting. They already establish the intended component-to-token relationship, so the ACSS card-to-button coupling should not be copied. Evidence: `lib/new_you_web/components/design/button.ex:1-80`, `assets/css/design-tokens.css:177-228`, `assets/css/design-components.css:1-85`.

**Attribute hooks: partial.** NewYou uses component-owned visual attributes such as button/card `data-variant` and button `data-treatment`; the design-system page also has local specimen attributes for alignment, viewport, treatment and measurements. The LiveView hook uses explicit data selectors for copy and preview behavior. This is scoped use, not a site-wide visual API. New component state should be owned by the Phoenix component and use native HTML/ARIA state where that state already exists. JS hooks should bind to narrow, documented behavior selectors, not infer presentation from arbitrary attributes. Evidence: `lib/new_you_web/components/design/button.ex:5-8`, `lib/new_you_web/components/design/card.ex:5-24`, `assets/js/design_system.js:1-90`.

## Decision and implementation contract

**Icons: adapt.** Keep Heroicons as the artwork source and retain the existing wrapper. If repeated icon presentation needs emerge, add a small Phoenix helper/component with explicit size/treatment inputs mapped to existing semantic tokens. Keep decorative icons hidden from assistive technology at the consuming component and require accessible names for icon-only actions on the native button/link. Do not add icon glyph CSS, a parallel asset library, or broad `[data-icon]` styling without a concrete use case.

**Cards: adapt.** Keep the existing `design_card/1` and its noninteractive `<article>` contract. Consider a media/avatar slot or named subcomponent only after a real repeated use case establishes required responsive and accessibility behavior. Keep card actions as native links/buttons; do not make every card a clickable wrapper. Preserve variant ownership inside the component and token-based styles.

**Data attributes: adopt selectively.** Continue using component-owned attributes for visual variants where Tailwind selectors or CSS rules need them. Keep caller attributes available for unrelated data, ARIA and LiveView needs; reject caller collisions for values owned by the component. Use native `disabled`, `aria-expanded`, `aria-selected`, and similar state when semantically applicable. For JS-only behavior, use narrow hook selectors and test lifecycle behavior. Never give generic `data-*` names implicit cross-component semantics. Defer inverted-radius implementation until a real page requires the decorative geometry and can prove forced-colors, contrast, responsive clipping and noninteractive semantics. Keep platform/editor selectors scoped to adapters.

Concrete implementation seams are `NewYouWeb.Components.Design.Icon` or a carefully extended `CoreComponents.icon/1`, `NewYouWeb.Components.Design.Card`, and token-mapped rules in `assets/css/design-components.css`. Exact additions remain deferred until repeated use and states justify them under §8.4. Candidate proof IDs and concrete acceptance steps:

- `COMP-ICONS-001`: render decorative and meaningful icons; assert decorative output is hidden from assistive technology and meaningful icon-only controls have an accessible name; assert the accepted size/treatment inputs map only to approved tokens; reject caller overrides for component-owned attributes; verify no glyph artwork is introduced by the styling wrapper.
- `COMP-CARDS-001`: retain the existing variant/native metadata/override/invalid-value tests; if a real use case adds media/avatar slots, render each supported shape and verify semantic image alternatives, intrinsic aspect/crop behavior at narrow and wide layouts, and keyboard behavior for adjacent native actions. Do not add speculative slot tests before the API exists.
- `COMP-DATA-ATTRIBUTES-001`: for each visual attribute owned by a Phoenix component, assert its generated value and collision rejection; assert unrelated `data-*`, ARIA and LiveView attributes survive; assert native states such as `disabled` remain native; for each JS hook, verify initialization/teardown and that its selector only targets its documented behavior. Keep inverted-radius and platform adapter attributes deferred unless implemented.

These are proposed proof identifiers; only the existing card coverage cited above is observed test evidence.

## Missing proof

- `COMP-ICONS-001`: no focused NewYou icon-wrapper accessibility or owned-size/treatment proof was located. Add the listed checks only with a concrete wrapper/API change.
- `COMP-CARDS-001`: current flat/raised variants, metadata forwarding, caller class/variant rejection, and invalid variant rejection are covered at `test/new_you_web/design_system_infrastructure_test.exs:87-190`. Responsive media/avatar contracts are absent because the API has no such slots; add proof alongside any justified future API.
- `COMP-DATA-ATTRIBUTES-001`: button/card tests cover current controlled visual-attribute collisions and unrelated metadata preservation, but no single catalog-wide proof checks icon ownership and JS hook scope/lifecycle. A targeted inventory test is only needed if those component surfaces expand.

## Icon token catalog and source hazards

The style map declares `--icon-scheme`, `--icon-size`, `--icon-padding`, `--icon-radius`, `--icon-background`, `--icon-background-hover`, `--icon-border-color`, `--icon-border-color-hover`, `--icon-border-width`, `--icon-border-style`, `--icon-color`, `--icon-color-hover`, `--icon-shadow`, `--icon-list-icon-size`, `--icon-list-gap`, `--icon-block-offset` and `--icon-inline-offset`. Two more families are `--icon-size-{xs,s,m,l,xl,2xl}` and `--icon-padding-{xs,s,m,l,xl,2xl}`. Null entries emit no token. The general default style is a selector/mixin input, not a `--icon-style` token.

The size-selector loop still iterates all six keys when the corresponding size tokens are omitted. Its declaration can therefore reference an undefined token. The boxed mixin's `solid` fallback does not rescue a defined `--icon-border-style:0`, because zero is not a valid CSS border-style keyword. These are source concerns that need configured/default compiler and computed-value proof, not verified runtime defects. A NewYou adaptation should choose finite, non-null token mappings and valid native CSS values directly. The configurable base attribute also does not rename every fixed `data-icon-*` or card `[data-icon]` hook; custom names need separate selector coverage. See `assets/scss/modules/icons/_vars.scss:3-93`, `_tokens.scss:1-23`, `_classes.scss:1-51`, `_mixins.scss:59-66`, and `assets/scss/modules/cards/_mixins.scss:91-110`.
