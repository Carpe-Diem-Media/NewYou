# P8-05 production-path proof

WELL-53 adds twelve P8-05 cases to the existing P8-04 runner. The approved entrypoint remains `test/proof/run.exs`. Run the commands in [phase8-proof.md](phase8-proof.md) through DevCore with TEST credentials.

The browser cases require Node.js and a local Chromium installation. The dependency-free CDP driver checks the standard Google Chrome and Chromium executable paths. It starts an isolated headless browser against the actual Phoenix endpoint on a loopback-only ephemeral TEST port. It submits the rendered forms with their CSRF tokens and operation IDs from the rendered forms. It checks the exact registry-backed EN and AF copy, pinned English legal artifacts, accepted registration, localized pending content and explicit resend. The TEST HTTP wrapper observes the actual Phoenix session keys before responses leave the endpoint. It creates no substitute registration endpoint or business write API.

No frontend source, participant copy, dependency, migration or business lifecycle is changed. Chromium stderr, screenshots, traces, page bodies and protected inputs are not saved. Synthetic credentials travel to the browser only on stdin. Returned browser evidence contains fixed boolean facts and opaque operation IDs. The driver closes Chromium through CDP, waits for its exit and confirms removal of its temporary profile before reporting worker cleanup. Runner assertions, rather than a browser-supplied PASS, decide each case verdict.

## Mappings and interpretation

`NewYou.Proof.P805Catalog` defines the case-to-obligation mapping and deterministic family digests. The fixed ten-family TB-001 inventory is unchanged. Only P8-05 obligations are mapped:

- `registration_pmr_reconciliation` contains accepted state, rejected gates, envelope rollback, registration replay/neutrality, PMR collision pressure, actual same-email contention, resend and immutable resend binding.
- `audit_e2` contains initial Audit schedule insertion failure and the subsequent source-transaction boundary, after all acceptance writes and before Ash commits.
- `browser_spine` contains separate English and Afrikaans registration/pending/resend journeys.

Evidence identifies the current routed `TB-001/v0.1.3` authority. Each mapping has explicit compiled `scope: :partial`, included in its deterministic digest. Only a reviewed `scope: :complete` manifest can produce a full-family PASS. Missing or invalid scope fails closed. The approved CLI uses only the compiled catalog and accepts no manifest or scope override. The pure evaluator accepts synthetic manifests for harness tests; it does not issue validated proof artifacts. Semantic result validation also rejects a partial-family PASS or omission of its `manifest.partial` reason.

These family entries describe the listed P8-05 cases. They do not certify later reconciliation, proof consumption, Audit materialisation, Communications execution or the full browser spine. When all twelve cases pass, their three family entries remain `completed`/`FAIL` with `manifest.partial`. Seven other required TB-001 families remain explicitly `missing`/`FAIL`. Thus all ten families remain unavailable for full certification and the overall `tb001` result remains non-zero and coverage-incomplete. Case PASS reports P8-05 assertion success separately from family completeness. Do not report TB-001, Phase 8, Phase 9 or production release readiness as passed.

The mechanism selection uses existing Ash Domain actions and owner-scoped private reads, AshPostgres transactions and constraints, the existing AshAuthentication password/token path, and the existing AshOban Audit schedule. Ash Signals and Temporal Resources are not applicable because this change introduces no runtime cross-Domain reaction or historical/as-of model. No extension is installed. Transaction and checkout behavior were checked against the installed dependency source and the [Ash 3.37.2 transaction reference](https://ash-project.github.io/ash/Ash.html#transact/3).

## Transactions, failures and concurrency

Each owner callback uses an independent, unboxed TEST PostgreSQL connection. The production Ash action owns its transaction and actual COMMIT. The proof adds no enclosing business transaction, advisory lock or substitute write path.

Envelope and Audit scheduling failures use scoped diagnostic PostgreSQL triggers. A temporary sequence records that the insertion cut actually ran despite rollback. Trigger bodies write no business state, and teardown removes their trigger, function and sequence.

The registration checkpoint is compiled only into TEST at the final return of `AcceptRegistration`, after Account/credential, PMR, Token, MessageIntent/envelope, Audit obligation/schedule and registration binding writes. Only the proof worker's process dictionary can bind it. Application input and runtime configuration cannot select a checkpoint. Production-build evidence checks both absence of all proof modules and absence of proof or Mix imports from the compiled owner module.

The source-boundary case arms the approved `transaction.before_commit` cut for a registered scenario worker. It observes the complete acceptance result inside the existing transaction, consumes the cut and verifies that fresh observations contain no partial consequence. Ash's injected exception is caught only in the proof worker; application exception/transaction behavior is unchanged.

The same-email case uses `Scenario` and `Concurrent` workers on independent PostgreSQL connections. It holds the first real acceptance transaction at that checkpoint and observes the second transaction blocked by the production uniqueness constraint through `pg_blocking_pids`. It records distinct transaction identities before releasing the first. There are no sleeps, synthetic business locks or sequential calls presented as a race. Fresh owning Ash reads establish the final result.

## Evidence and teardown

Callbacks report bounded booleans, counts and classifications through the runner assertion ledger. Passwords, password hashes, verification bearers, envelope ciphertext, keys, URLs and participant email are never proof observations. The accepted-state case inspects persisted rows for raw password and bearer absence without returning row contents. Audit job arguments must equal the approved primary-key envelope containing only `EvidenceObligation.id` as its business reference. No Communications job is required, and no Communications/Audit worker or provider runs.

Fixture teardown is diagnostic SQL under TEST support, never a business mutation API. It removes only synthetic rows bound to pre-registered fixture emails and operation IDs, plus their delivery/Audit consequences. It recovers operation IDs submitted by the browser from durable owner provenance if browser reporting fails. Successful cleanup requires checkin after the source transaction has ended. Cleanup starts unconfirmed for P8-05 callbacks, so interruption cannot inherit a successful connection/lock verdict.

Permanent PMR reservations remain permanent, matching the existing Identity test contract. They contain no fixture email or credential. All other fixture consequences and diagnostic DDL are removed. Nonce records associated with removed envelopes are also removed.

### WELL-14 fixture termination correction

At implementation SHA `f88b1842b94907c576121eb142a5321873b6fb17`, [P805](../../test/support/proof/p8_05.ex) synchronously registers synthetic identifiers with a separate cleanup guardian before writes. If the callback dies, the guardian cleans only that fixture's durable consequences on its own connection and restores the captured application environment. [Scenario](../../test/support/proof/scenario.ex) awaits the guardian and propagates cleanup failure before completing worker teardown. Normal cleanup retains the guardian until database cleanup and environment restoration finish. This closes the previous gap where a killed process could not execute its `after` block.

The [owner-death regression](../../test/new_you/proof/p8_05_test.exs) kills a worker after committed registration, waits for Scenario teardown, then checks fixture counts and MFA-environment restoration. Permanent PMR reservations remain. The aggregate catalogue test now has a finite 600-second ExUnit budget for all compiled families and independent BEAM boots. Per-case manifest deadlines remain unchanged. This corrects test execution and cleanup; it does not change business authority or increase certified proof coverage. Final hosted application results belong in WELL-14 and PR #204.

### WELL-14 disconnected-lease and browser-startup correction

At proof implementation SHA `f0e2d35a4d3b628802f87e856411f9299f10614f`, [P805.with_fixture/1](../../test/support/proof/p8_05.ex) acquires a fresh unboxed connection for normal teardown. A bounded task borrowing the fixture connection can disconnect its lease when its query times out. The previous unconditional check-in then raised `:not_found`, masking the callback's result or error. Ecto's existing `Sandbox.unboxed_run/2` releases any remaining lease, opens the teardown connection and ensures its check-in. Fixture scope, guardian recovery and permanent PMR reservations are unchanged. The [connection-loss regression](../../test/new_you/proof/fixture_connection_test.exs) reproduced the exact teardown failure with a real cancelled PostgreSQL query before the fix; it verifies that teardown completes and removes the committed synthetic Account afterward.

The [Chromium driver](../../test/proof/p8_05_browser.mjs) now waits for `Browser.getVersion` before creating its browser context. [Protocol coordination](../../test/proof/browser_protocol.mjs) gives startup and all ordinary commands one shared 40-second work budget. Individual command deadlines remain at most 20 seconds, capped by the remaining work time. Shutdown has time reserved through the 44-second boundary, inside the existing 45-second Elixir port deadline; proof-case deadlines are unchanged. No command or page assertion becomes successful merely because readiness completed. Startup and context failures still fail the proof with allow-listed codes.

The [protocol regressions](../../test/proof/browser_protocol_test.mjs) use a controlled clock to reproduce a delayed startup consuming the old context deadline. They also verify bounded unresponsive startup, propagation of context failure and a readiness response near the work deadline that leaves only the remaining time for context creation. Independent review identified that final deadline interaction; its regression failed before the shared-budget correction and passes afterward. The hosted `p807.browser_en` timeout is consistent with startup delay, but its bounded output did not expose the underlying Chromium exception. A fresh hosted run remains required to validate the correction.

These are test-support changes. Application source, dependencies, configured authentication, participant copy and canonical Assent inputs are unchanged.
