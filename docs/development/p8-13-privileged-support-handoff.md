Revision 3 describes [WELL-14](https://app.plane.so/symphony-development/browse/WELL-14), implemented at Git SHA `f88b1842b94907c576121eb142a5321873b6fb17` on `feat/well-14-privileged-support`. The documentation commit is separate. Future readers must compare current source, dependency pins, routed authority and live Plane with that SHA before reusing this map. Production use remains subject to the governing authentication and release requirements. ## 2. Architecture, sequence and ownership

The supported entry points are [Identity](../../lib/new_you/identity.ex) functions `enroll_privileged_mfa/2`, `confirm_privileged_mfa/3`, `step_up_privileged/4`, `place_security_hold/1`, `review_security_hold/1` and `release_security_hold/1`. Existing password or magic-login credentials identify a durable Session; caller-supplied role or assurance claims grant nothing.

The release sequence in [SecurityHold](../../lib/new_you/identity/security_hold.ex) is:

1. `preflight/1` locks and checks current Identity authority and the held generation's independent review.
2. [Audit.admit_security_hold_release/1](../../lib/new_you/audit.ex) commits or replays a bound E1 admission in its own transaction. It refuses an existing outer transaction.
3. `attempt_release/2` opens a separate Identity transaction. `authority/2` and `held_and_reviewed/2` reread current Accounts, Session, Token, scoped grant, MFA versions and review authority. E1 never reserves permission.
4. The private Account release action changes posture and source operation result together with a linked Audit E2 obligation and its existing durable schedule.
5. The [existing Audit executor](../../lib/new_you/audit/actions/materialize_registration_evidence.ex) materialises that obligation independently. Its legacy registration name remains for worker/job compatibility. It never reads or mutates Identity.

Identity owns grants, MFA, Session assurance, review eligibility, hold posture and source operation outcomes. Audit owns admission and evidence assertions. The source transaction can roll back without erasing the earlier admission. No provider call, browser state, process-local authority or external I/O participates in these commits. [P8-13 proof](../../test/support/proof/p8_13.ex) exercises the separate boundaries.

## 3. Ash map

[Account](../../lib/new_you/identity/account.ex) adds restricted MFA fields, `security_version`, `hold_version`, `hold_review` and `hold_operations`. `update_privileged_mfa` is an internal write action. `invalidate_grant_assurance` atomically advances the Account security version when a grant is revoked. Private `place_security_hold`, `review_security_hold`, `release_security_hold` and `record_security_hold_attempt` actions apply conditional held-generation filters. Callers use the Identity owner functions, not these primitives directly.

[IdentityGrant](../../lib/new_you/identity/identity_grant.ex) is the only added business Resource. A grant assigns the governed Support role and a bounded scope for one target Account, with a subject, independent approver, validity and revocation/version state. Under [Product §15.1A](../governance/product/00_PLATFORM_v1.14.0.md), `permits?/2` derives capabilities from the role/scope catalogue: `security_hold_restriction` permits placement, `security_hold_review` permits review, and `security_hold_release` permits release. There is no accepted or persisted per-subject capability input. [PrivilegedAccess](../../lib/new_you/identity/privileged_access.ex) and the independent-review recheck both use this catalogue, then check current subject, target and lifecycle authority separately.

The Resource's ordinary policy denies direct callers. The synthetic `provision` action exists only in development/test builds and is absent when the Resource is compiled for production. [The production-compilation regression](../../test/new_you/identity/identity_grant_test.exs) checks that boundary in an isolated BEAM. Private `revoke` remains an owning transition with no public runtime grant-management endpoint. The `one_active_assignment` identity uniquely binds subject, role, scope and target while state is `active`; changing approver, reason or dates cannot duplicate it. Expiry is checked at use without waiting for cleanup. An expired row still marked active requires explicit revocation before replacement.

[Session](../../lib/new_you/identity/session.ex) stores purpose, verification/expiry time and bound MFA/security versions. `set_step_up` and `clear_step_up` are private. Logout, revocation and Session expiry clear assurance fields. The [grant revocation change](../../lib/new_you/identity/changes/invalidate_grant_assurance.ex) locks the subject Account, rereads current grant state, advances the security version and clears that Account's existing elevated Session fields before the conditional grant write. Its `after_action` establishes selected `identity_grant_revoked` E2 work through Audit in that same transaction. A repeated revocation returns its committed result without clearing later assurance or creating another obligation. Token presence and revocation remain with the existing [Identity Token](../../lib/new_you/identity/token.ex) and AshAuthentication stack.

[EvidenceRecord](../../lib/new_you/audit/evidence_record.ex) distinguishes E1 admission from an E2 materialisation. Admission has an explicit action class and unique attempt identity; materialisation has one record linked to its immutable obligation. [EvidenceObligation](../../lib/new_you/audit/evidence_obligation.ex) extends selected E2 work to security placement, review, MFA confirmation, grant revocation and linked release outcomes. Its narrow AshOban policy allows only executor reads/materialisation. EvidenceRecord's ordinary policy denies direct access.

Ash actions, PostgreSQL row locks and constraints implement the required behavior. Signals were considered and not selected because authoritative admission/effect ordering is synchronous. Temporal Resources are not needed for this current-state and append-only-evidence contract. No StepUp/MFA/hold Resource or extra service is introduced.

## 4. Important interface contracts

`credentials` is the existing `%{session_id: uuid, token: bearer}` transport. Bearers, passwords and TOTP codes are transient and sensitive. MFA enrollment returns `{:ok, %{secret: binary}}` only after current Session and password reauthentication. Confirmation and step-up return `{:ok, :ok}` or `{:error, :privileged_access_unavailable}`. Enrollment remains pending until proof of possession. A reauthenticated retry while pending returns the same setup factor without changing its ciphertext or versions, including after response loss or restart. A revoked/expired Session cannot resume setup, and an active factor never returns setup material. Confirmation and its selected E2 obligation commit together. See [PrivilegedAccess](../../lib/new_you/identity/privileged_access.ex) and its [tests](../../test/new_you/identity/privileged_access_test.exs).

The step-up purpose is exactly one of `:place_security_hold`, `:review_security_hold` or `:release_security_hold`. The implementation uses a five-minute assurance lifetime and a private five-failure, fifteen-minute cooldown. These are bounded implementation controls, not a declaration that OQ-035's broader abuse/escalation policy is resolved. Failed password reauthentication at enrollment, confirmation and step-up consumes the durable Account failure budget once the current-Session boundary passes. Rejected TOTP attempts use the same budget; malformed requests and invalid Sessions fail before this boundary. Expected denials commit counters; operational errors roll back security transitions and evidence obligations.

Each hold function accepts exactly `%{credentials: map, grant_id: uuid, target_id: uuid, expected_version: non_negative_integer, operation_id: uuid, reason_code: atom}`. Allowed reasons are `:suspected_compromise`, `:security_review`, `:verified_recovery` and `:mistaken_hold`. Success returns `{:ok, %{status: :held | :reviewed | :released, version: integer}}`; unavailability returns `{:error, :security_hold_unavailable}`. The operation binds kind, actor, grant/version, Session, expected generation and reason in Account-owned source state. Changing that binding cannot replay the prior result. See [SecurityHold.binding/3 and prior_result/3](../../lib/new_you/identity/security_hold.ex).

Audit's admission input accepts only attempt, actor, target, grant/version, Session, expected generation and bounded reason. Audit sets the action class and admission time. It returns a committed EvidenceRecord or `{:error, :evidence_admission_unavailable}`. The trusted source-only `establish_identity_security_obligation/1` requires an existing source transaction and returns the obligation or an error. It is not a public authority endpoint. See [PrivilegedEvidence](../../lib/new_you/audit/privileged_evidence.ex).

The private grant `revoke` action requires `actor_id` and a reason of `:security_review` or `:suspected_compromise`. Its E2 envelope identifies that actor, the affected subject Account, grant, revocation timestamp and successful outcome. Identity generates a fresh operation UUID so a caller-selected hold operation cannot reserve the revocation's evidence key. The committed obligation retains that identity for executor recovery. Runtime grant-management approval and actor authorization remain prerequisites for any future public caller.

## 5. Lifecycle, failure and recovery

MFA progresses `disabled` to `pending` to `active`. Factor reset/disable and broad enrollment UX are not implemented. Account locks serialize validation and advancement of the accepted TOTP period; validation uses that same captured period. Active step-up also checks current Account eligibility, MFA/security versions, durable Session/Token state and exact purpose/expiry. Device or browser assertions cannot substitute. [MFA tests](../../test/new_you/identity/privileged_access_test.exs) cover replay, independent transactions, persisted cooldown and deterministic period boundaries. [Enrollment regressions](../../test/new_you/identity/mfa_enrollment_test.exs) cover failed-password admission, concurrent pending retry, fresh-BEAM resume/cooldown, Session expiry/revocation and active-factor non-disclosure.

Grant revocation invalidates every existing elevated Session for its subject and increments the current Account security version. A replacement grant cannot reuse earlier assurance. Fresh password/TOTP verification is required. Revocation replay leaves later assurance and the original evidence obligation intact. A failed grant write or E2 establishment rolls back all invalidation. A later materialisation failure leaves the grant revoked and its durable obligation recoverable; Audit recovery never replays Identity. [Revocation tests](../../test/new_you/identity/grant_revocation_test.exs) cover replacement, concurrent idempotency, both rollback boundaries, operation-ID collision denial and fresh-BEAM materialisation/replay.

Placement changes `normal` to `held`, increments hold/security versions, clears earlier review and revokes active target Sessions. Review records a current scoped reviewer distinct from the target. Release also requires that reviewer to differ from the releaser, and checks the reviewer's current grant and Account/MFA/security versions. Release changes only security posture; it does not verify email, reopen an Account or complete recovery. Review never releases a hold. [Hold tests](../../test/new_you/identity/security_hold_test.exs) cover these checks and invalidation after admission.

Account locks use stable ID order before Token/Session/grants. The lock set includes the current reviewer; a newly changed review requiring an unlocked Account fails closed. Conditional generation filters arbitrate source transitions. Successful same-operation retries return the stored result without a second transition. Distinct admitted attempts remain distinct evidence, including a losing contender. See [SecurityHold](../../lib/new_you/identity/security_hold.ex) and [race proof](../../test/support/proof/p8_13.ex).

Admission failure prevents release. A known source failure rolls back the effect, then records a source-owned failed result with a linked E2 obligation in a fresh transaction. If that recording boundary is also unavailable, the admission remains unresolved; no fabricated success/failure evidence is written. A retry reconstructs current authority and source result before proceeding. Audit cannot infer permission or replay the source. Hard termination after E1 leaves the admission and held posture; same-attempt retry can proceed through fresh authorization. Hard termination after source COMMIT leaves the source result and obligation; Audit can recover materialisation without changing source truth. The [P8-13 driver](../../test/support/proof/p8_13.ex) and [restart helper](../../test/proof/p8_13_restart.exs) exercise both cuts.

## 6. Persistence and consistency

[The schema migration](../../priv/repo/migrations/20261107184110_well14_privileged_support.exs) adds Account MFA/hold fields, Session assurance, scoped grants and minimal Audit envelope fields. Grant foreign keys, independent-approval and validity checks protect the source representation. Hold versions are nonnegative and source operation bindings are objects. Existing Account data receives disabled MFA, no assurance and an empty hold-operation map.

[The evidence guard migration](../../priv/repo/migrations/20261107184116_preserve_privileged_evidence_provenance.exs) retains the existing append-only record and obligation protections and extends immutable provenance comparison to all envelope fields. Release results must match their admission's attempt/actor/target/grant/Session/reason. [The final constraint migration](../../priv/repo/migrations/20261107185520_well14_evidence_class_and_grant_guards.exs) adds explicit action classification, strict admission/materialisation shapes and grant state/revocation consistency. [The active-assignment migration](../../priv/repo/migrations/20261108052448_well14_identity_grant_unique_active_assignment.exs) adds the partial unique index matching the Ash identity. Existing duplicates cause migration failure rather than silent reconciliation. Schema rollback refuses to discard new security or admission data without governed disposition. These are ordinary-write guards, not protection against a database owner disabling triggers.

[The scope migration](../../priv/repo/migrations/20261108073818_well14_role_scopes.exs) renames the old capability column to scope and maps each old value to its corresponding bounded Support scope. The mapping preserves the existing authority without widening it. It rebuilds the active-assignment identity over role/scope/target and refuses rollback while grant history exists. It does not invent missing historical approval or evidence for synthetic rows created by earlier unmerged revisions.

TOTP secrets stay in encrypted Account attributes and are not decrypted by default. [MfaVault](../../lib/new_you/identity/mfa_vault.ex) implements AshCloak's callbacks using the existing Plug.Crypto 2.2.1 authenticated encryptor, with purpose/version AAD and bounded envelope parsing. It introduces no custom cipher or authority process. [Vault tests](../../test/new_you/identity/mfa_vault_test.exs) exercise randomised ciphertext, tamper rejection, retained-key rotation and unavailable-key failure.

Runtime key injection uses `NEWYOU_IDENTITY_MFA_ACTIVE_KEY_VERSION` and `NEWYOU_IDENTITY_MFA_KEYS_JSON` in [runtime configuration](../../config/runtime.exs). Keys are separate from database, token-signing and Communications keys. New writes use the active key; old ciphertext requires its explicitly retained key. Missing or invalid material fails closed. The random [test-only keyring](../../config/test.exs) is ephemeral and cannot serve as a persistent deployment key. No key value belongs in source, evidence or this map.

The proof includes genuine PostgreSQL contention with distinct connections/transaction IDs, same versus distinct attempts, injected admission/source failure, process termination at both committed boundaries, and independently booted current-authority/outcome checks. Fixture-only SQL seeds controlled invalidation and tears down synthetic records while restoring guards transactionally. [P813HoldFixture](../../test/support/proof/p8_13_hold_fixture.ex) resets TOTP replay state only while arranging separate fixture capabilities; the replay race itself does not reset it. Test-only seams are compiled out of production.

Owner death triggers scoped cleanup on an independent connection and restores the captured fixture environment, including the MFA keyring. [Scenario](../../test/support/proof/scenario.ex) waits for that guardian before reporting worker teardown and propagates cleanup failure. The [forced-owner-death regression](../../test/new_you/proof/p8_05_test.exs) checks immediate post-teardown counts and environment restoration, while retaining permanent PMR reservations. The aggregate catalogue test has a finite 600-second budget for all owned families and fresh BEAM boots; individual proof deadlines are unchanged. ## 8. Future-agent extension guide

Start at the Identity owner functions, then follow `PrivilegedAccess.authorize_locked/4`, the role/scope catalogue, `SecurityHold.preflight/1`, Audit admission, the separate `source_transaction/3`, private Account action and E2 obligation/executor. Read the five migrations and the catalog's matching assertions. The map's source locators were checked against the implementation SHA above; final independent review must also inspect its documentation head.

Future grant provisioning must supply its governed approver/bootstrap and E1 activation semantics before exposing a runtime interface. Future revoke/reset/recovery work must preserve selected E2/E1 evidence and version invalidation. Reuse owner interfaces; do not promote the private primitives into routes, use DeviceAssurance for high-risk step-up, treat an admission as a bearer capability, or replay Identity from Audit jobs. WELL-15, WELL-16 and WELL-18 remain separately governed downstream work in Plane.

Cold-start walkthrough: the Domain functions resolve to the two internal Identity modules; the Account actions expose conditional generation filters; role/scope, grant/MFA/Session checks remain in the current locked path; the admission has an independent commit; source result plus obligation share a later commit; the executor contains no Identity call; and the named tests/catalog cover those same boundaries. Revision 3 also follows production provisioning exclusion, the Account-first revocation/E2 transaction and forced fixture cleanup through their regressions. Source and tests remain the authority for what currently runs.
