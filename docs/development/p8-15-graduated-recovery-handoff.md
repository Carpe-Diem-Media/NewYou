## 2. Architecture, sequence and ownership

1. [RegistrationBoundary](../../lib/new_you_web/registration_boundary.ex) dispatches the five recovery routes through the existing browser/CSRF pipeline without full-connection router telemetry. [PrivacyTelemetry](../../lib/new_you_web/privacy_telemetry.ex) scrubs recovery metadata. [RecoveryController](../../lib/new_you_web/controllers/recovery_controller.ex) requires a dev/test fixture build and `p8_15_browser_development_fixtures`. GET/HEAD returns an empty, non-consuming response. POST responses are uniformly empty. No participant wording or visual composition was added.
2. [Identity](../../lib/new_you/identity.ex) exposes the supported recovery interfaces. [Recovery.request/3](../../lib/new_you/identity/recovery.ex) canonicalizes email, applies a 250 ms database-transaction timeout and a common 500 ms response floor, and returns `:ok` for known, unknown and malformed requests. This is not a guarantee against arbitrary scheduler or host delays.
3. The request locks Account before case/proof authority. It reuses the active case or creates a [RecoveryCase](../../lib/new_you/identity/recovery_case.ex) and an existing Identity [Token](../../lib/new_you/identity/token.ex). A verified channel gets a purpose-bound proof and a durable held Communications obligation in the same transaction. An unverified channel creates a zero-assurance `held_manual_review` case without changing Account posture, credentials, Sessions or Devices. That case state is not an Account security hold. The existing Identity verification action can establish the channel; a same-operation retry then issues a recovery proof on the same case without reducing its requirement. Only proof-backed escalation can impose a new Account hold, with a selected E2 obligation in the same transaction.
4. Explicit proof submission validates the current Token and Account binding, consumes the proof and advances durable case assurance atomically. Delivery and passive retrieval cannot advance it.
5. Ordinary completion calls `Recovery.finish/6` under the Account lock. Credential replacement, Session/Device revocation, registration-binding invalidation, E2 obligation plus initial Audit scheduling, required notice obligation and completed case share one transaction. No Session is created.
6. [ManualRecovery](../../lib/new_you/identity/manual_recovery.ex) adds current scoped staff authorization, an independent approver and independently committed Audit E1 before each exceptional approval and completion. Communications owns delivery obligations; Audit owns evidence. Neither owns recovery truth.

## 3. Ash map

[RecoveryCase](../../lib/new_you/identity/recovery_case.ex) uses AshPostgres, AshStateMachine, private actions and deny-by-default policies. Its generic actions delegate to [Actions.Recovery](../../lib/new_you/identity/actions/recovery.ex). The Identity wrapper invokes the owning action and normalizes errors. Private resource actions are not caller authorization substitutes.

[Account](../../lib/new_you/identity/account.ex) owns current security posture, MFA and credential/security generations. RecoveryCase owns its monotonic required/satisfied assurance. No permanent Account recovery floor remains. Token uses the pinned AshAuthentication `StoreTokenChange`, with fixed claims rather than a signed bearer. `recovery_case_id` has a FK and unique proof identity. Existing [Session](../../lib/new_you/identity/session.ex), [DeviceAssurance](../../lib/new_you/identity/device_assurance.ex), [IdentityGrant](../../lib/new_you/identity/identity_grant.ex) and [PrivilegedAccess](../../lib/new_you/identity/privileged_access.ex) remain authoritative for their existing security facts.

[Ash Signals](../../.agents/skills/ash-framework/references/ash/signals.md) were considered and are not used for required Communications/E2 acceptance because their results are required before source commit. Temporal Resources are not needed for current case state plus append-only provenance. Existing AshOban owner schedules remain in use. No dependency, Repo, token store, generic workflow engine, Redis or process-local business authority was added.

## 4. Interface contracts

- `Identity.request_recovery(email, locale, operation_id)` returns only `:ok`. It creates no login or email verification. A duplicate request never reduces current-case assurance or imposes a security restriction. An elapsed active case becomes expired; retrying its operation cannot reopen it. A fresh operation may create a successor using current Account requirements.
- `submit_recovery_proof(proof, operation_id)` returns `{:ok, :accepted}`, a terminal `:failed`/`:expired` outcome, or the common recovery error. The same committed acceptance operation is replay-safe. Different proof purposes and revoked proof fail closed.
- `complete_recovery(proof, password, operation_id)` returns `:completed` once and `:already_completed` for its committed operation receipt. Changed password input on that retry is ignored. A different completion operation cannot replay the effect. The current password is rejected without consequences.
- `approve_manual_recovery(request)` takes current credentials, scoped grant, case/version, operation ID and `:verified_recovery` reason. It returns an approved case version. Approval replays only its bound operation and authority. `complete_manual_recovery/1` additionally takes the replacement password, requires a distinct current actor and returns the completed receipt.
- `cancel_recovery/2` terminates a current claimant-bound case. Completed, failed, expired and cancelled cases cannot reopen.
- `recovery_delivery/3` is a trusted transaction-only serialization seam. It returns a transient bearer only for the current proof/destination/locale. It supplies no content or provider permission.
- `DeliveryEligibility.recovery/4` is a read-only transaction-only source guard for the exact issuance operation, proof, destination and locale. It shares Account/case/Token locks and current/expiry checks with serialization and returns only `:ok` or `{:error, :source_invalid}`.
- `DeliveryEligibility.recovery_notice/3` validates the terminal completion receipt, source proof linkage, completion operation and case locale. Later credential changes, proof expiry or revocation cannot erase a committed notice. Communications owns its immutable original destination. This guard never serializes a bearer or grants Content/provider permission. Executor does not yet invoke either recovery guard because the recovery admission gate remains closed.

See the actual typespecs in [Identity](../../lib/new_you/identity.ex) and action guards for complete return/input details.

## 5. Lifecycle, failure and recovery

The state enum is `requested`, `proof_pending`, `additional_assurance`, `held_manual_review`, `completed`, `failed`, `expired`, `cancelled`. State is separate from required and satisfied assurance. The selected ordinary representative uses a verified-channel proof. MFA-enabled, privileged, held or unverified Accounts require the stronger floor. A live case preserves its established requirement even if a later fixture representation of current risk is lower. A successor uses current Account security, MFA and grants after its predecessor is terminal. A current higher requirement still applies to every new case. There is no automatic Account policy reset. It implements no general risk scoring or new recovery factors.

A case lives for one hour; initial proof consumption requires the original 15-minute validity. Once consumed, assurance is durable. Manual completion checks the consumed proof/case linkage and current case deadline, not the expired delivery-link lifetime. Staff review expires no later than its case, grant and five-minute step-up. Staff Accounts lock in sorted order before Token/Session/grant/case locks. Final completion rechecks both people, grants, MFA/security generations, Session/step-up, case version, hold version, Account binding and E1 envelope.

An unavailable ordinary channel creates only a case-level review pause at zero assurance. It cannot restrict the Account or create a verified-recovery Audit claim. Existing email verification may restore the ordinary channel, after which a bound retry resumes the same case. The binding permits only that false-to-true verification change; changed email, credentials or security generations cannot be silently rebound. If no approved ordinary factor is available, proof-independent manual completion remains fail-closed. The owner selected bounded Option B in WELL-111; the live supplementary acceptance now explicitly covers bounded zero-factor denial as described below. No document-based or operator-discretion substitute is implemented. Manual completion requires an already accepted verified-channel proof plus two current scoped staff actors. A proof-backed hold remains after case completion, failure, cancellation or expiry until the existing P8-13 independent review/E1 release boundary authorizes release. A case terminal is not release authority. Tests exercise the real release interface after manual completion, then prove a fresh case uses current requirements without the former permanent floor. Sensitive email change is blocked by the database while held; implemented MFA/login/reset paths also reject held authority.

Manual approval and completion each perform a locked preflight, commit their case-bound E1 admission, then revalidate current authority in a new source transaction. Approval records a linked review outcome atomically with the case version. Failed review operations cannot later become successful reviews. Failure before source commit rolls back the complete acceptance. E1 remains an admitted attempt after source failure. A caught failed source attempt records a linked failed E2; that failed operation cannot later become success. Process death after E1 can leave no outcome yet. The pending case and admission survive, and retry of that operation revalidates current authority and completes once. A changed or unavailable current authority never permits replay of the protected effect.

Cases bind the original Account email, credential/security/hold/MFA generations, case requirement and signing configuration through a keyed digest. The last v1 digest member now comes from the immutable case requirement rather than the removed Account field. Existing valid case bindings remain compatible without rewriting history. A later competing Account change invalidates the old binding. Real PostgreSQL tests prove completion races with password login and password reset. The P8-16 primary-email owner API is not implemented here. Its future mutations must preserve the same Account lock and current-version contract; the email-change tests represent an earlier owner commit through a fixture, including genuine PostgreSQL blocking and recovery re-read after that commit. The real recovery interface rejects the stale proof, fails its case and revokes its proof without overwriting the newer email. There is no current Account update action accepting email. This is not proof of the future complete P8-16 workflow.

[Communications.establish_recovery/1 and establish_recovery_notice/1](../../lib/new_you/communications.ex) create distinct causal roles on the existing [MessageIntent](../../lib/new_you/communications/message_intent.ex). Their content binding is absent, disposition held and reason `content_ineligible`. Existing message roles still require every content binding field. The [executor](../../lib/new_you/communications/executor.ex) rejects provider admission for recovery roles. No bearer, rendered URL/body or submitted password is stored in an intent, case, Audit payload or job argument. Recovery Token metadata survives framework expiry cleanup so it cannot erase a pending case's accepted assurance or completed receipt. This is not a new Privacy retention policy.
