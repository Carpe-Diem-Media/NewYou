## Owner interfaces and transaction boundaries

[Identity's acceptance action](../../lib/new_you/identity/actions/accept_registration.ex), `AcceptRegistration.run/3`, still owns Account/PMR/Token and the accepted source result. It calls [Audit](../../lib/new_you/audit.ex), `establish_registration_obligation`, through the owning Ash interface. [ScheduleRegistrationEvidence.change/3](../../lib/new_you/audit/changes/schedule_registration_evidence.ex) inserts the initial Audit executor job within the source acceptance transaction. Failure in obligation creation, enqueue or later acceptance work rolls back the complete acceptance boundary. No source action or acceptance write changes in WELL-11.

The internal Audit interface is `Audit.materialize_registration_evidence(%{primary_key: %{id: obligation_id}}, authorize?: false)`. It returns `{:ok, %{obligation_id: id, evidence_record_id: id}}` or an Ash error tuple. The generated [AshOban worker](../../lib/new_you/audit/evidence_obligation.ex), `NewYou.Audit.Workers.RegistrationEvidence.perform/1`, invokes that same private transactional Ash action. Invalid/missing selectors fail; they never create source truth. These callable internal functions do not confer participant/operator authorization.

[MaterializeRegistrationEvidence.run/3](../../lib/new_you/audit/actions/materialize_registration_evidence.ex) acquires `Ash.Query.lock(:for_update)` on the obligation inside the existing Ash transaction before reading assertion state. The transaction includes both Audit Resources. It creates or reuses the record, then calls the private `:fulfill` action. Record insertion and fulfilment commit together on the normal executor path. The executor never calls Identity or Communications. PostgreSQL row serialization and unique indexes establish correctness; executor uniqueness only reduces redundant work.

## Lifecycle and recovery

The only obligation states remain `open` and `fulfilled` in [EvidenceObligation](../../lib/new_you/audit/evidence_obligation.ex). [FulfillEvidenceObligation](../../lib/new_you/audit/changes/fulfill_evidence_obligation.ex) checks record presence; database guards also protect that invariant.

- An open obligation without a record creates one assertion and fulfils in the same transaction.
- An open obligation with a record reuses its existing ID and fulfils. This is a supported recovery input. The current executor cannot commit this intermediate state during an ordinary crash because its insert and fulfilment are atomic. The proof constructs it through the existing private record action and labels that distinction.
- A fulfilled obligation returns its existing record without another insert or update. Database guards prohibit reopening or changing terminal provenance.
- A fulfilled obligation with no record fails with `evidence_obligation_integrity_mismatch`. It does not fabricate a replacement assertion or replay Identity. The job's obligation ID and bounded error identify the operational failure. Manual source repair, restore adjudication and governed correction are separate work.

The existing AshOban trigger now has `scheduler_cron "* * * * *"` and discovers open obligations directly from PostgreSQL using its paginated read action. [Application startup](../../lib/new_you/application.ex) already feeds `AshOban.config/2` into Oban; [Oban configuration](../../config/config.exs) provides the cron, retry and lifeline machinery. The scheduler recreates absent or exhausted execution work after a fresh boot. An incomplete job may deduplicate scheduling; Oban retains its retry/recovery responsibility. A discarded/completed/removed job cannot erase the open obligation. No new daemon, service, Domain, Resource or dependency is introduced.

A duplicate executor may wait on the obligation row. After the first transaction commits, it reads the committed terminal state and returns the same assertion. If the first process dies after insertion but before commit, PostgreSQL rolls the record back and releases its lock; a fresh executor retries the still-open obligation. No extra business states represent attempt counts or queue status.

## Persistence and privacy

[The original evidence migration](../../priv/repo/migrations/20261030161752_well50_registration_evidence.exs) retains one source-operation obligation and one record per obligation through unique indexes, the record-to-obligation FK and lifecycle/timestamp checks. [The WELL-11 migration](../../priv/repo/migrations/20261106070000_harden_audit_e2_invariants.exs) adds:

- `evidence_obligations_lifecycle`, which requires initial `open`, freezes IDs/type/source operation/source time/creation time, prohibits terminal mutation and requires a record before fulfilment;
- `evidence_records_immutable` and `evidence_records_no_truncate`, which reject ordinary assertion update, delete and truncate;
- obligation delete/truncate guards, which preserve outstanding work and retained provenance.

The migration takes Access Exclusive table locks for existing fulfilled-record validation and guard installation in one transaction. Lock duration depends on existing data and database activity. It rewrites no data. Existing inconsistent fulfilled rows fail validation with a bounded error and require investigation. Open rows with existing records remain valid recovery inputs. Down removes guards/functions without deleting rows and weakens protection, so reversal needs operational review. Local down/up execution passed. Test fixture cleanup temporarily disables only named deletion guards under transactional table locks, deletes only tracked synthetic rows and restores the guards before commit. This is [TEST teardown](../../test/support/proof/p8_05.ex), never an application interface. The existing [Identity race-test teardown](../../test/new_you/identity/registration_orchestration_test.exs), `cleanup_unboxed_registration_rows/2`, similarly restores the obligation deletion guard inside its enclosing transaction. Those tests do not materialise EvidenceRecords.

These guards reject ordinary SQL mutation, but a database owner or superuser can deliberately disable/drop them. They are not an infrastructure tamper-proof guarantee or an implemented lawful-disposition workflow. Retention, correction/supersession and restore adjudication remain separately governed. The existing two Audit Resources and Domain ownership do not change.

[EvidenceRecord](../../lib/new_you/audit/evidence_record.ex) still stores only its ID, obligation reference and actual creation time. Immutable obligation provenance retains the original source operation, source event time and selected evidence class. Delayed record creation does not relabel that source time as materialisation time. Job arguments contain only the obligation business selector plus empty AshOban metadata/action arguments and nil tenant. No bearer, password/hash, destination, Account snapshot, protected envelope or provider payload is added. Source snapshots used by proof exist only in test memory; reports contain assertion identifiers and booleans.

## Framework selection

USE the installed Ash actions, AshPostgres transaction and row-lock APIs, existing PostgreSQL identities/FK/checks, and generated AshOban scheduler/worker. The pinned versions are Ash 3.37.2, AshPostgres 2.15.2, AshOban 0.10.2 and Oban 2.24.2 in [mix.lock](../../mix.lock). Material API facts were checked against installed source and version-matched official [Ash query documentation](https://hexdocs.pm/ash/3.37.2/Ash.Query.html#lock/2), [AshPostgres documentation](https://hexdocs.pm/ash_postgres/2.15.2/AshPostgres.DataLayer.html), [AshOban DSL](https://hexdocs.pm/ash_oban/0.10.2/dsl-ashoban.html) and [Oban documentation](https://hexdocs.pm/oban/2.24.2/Oban.html). In this pinned AshOban version, the generic-action worker calls `Ash.run_action!`; its update-action row-lock implementation does not protect the generic action. Audit therefore takes the lock itself.

Ash Signals were considered for cross-Domain reactions. They are not selected because acceptance already requires the owning Audit call to succeed and return within the source transaction; replacing that established seam adds no needed capability. Temporal Resources are not applicable to this append-only assertion plus two-state obligation model. No historical/as-of mutable Resource query is required. AshStateMachine/history extensions and new dependencies are unnecessary. Igniter's supported generators/refactors do not express these existing-action changes or bespoke database triggers; the focused hand edits and explicit migration preserve existing Resources. `mix ash.codegen --check` passed without generated schema changes.

## Executable proof and limits

[Registration evidence tests](../../test/new_you/audit/registration_evidence_test.exs) exercise atomic source acceptance and initial schedule, replay, recovery with an existing record, scheduler configuration/discovery, database uniqueness/FK/lifecycle/immutability, corrupt terminal fail-closed behavior and rejected selectors/excess payload. [E2RecoveryTest](../../test/new_you/audit/e2_recovery_test.exs) executes four [P811 catalogue cases](../../test/support/proof/p8_11_catalog.ex) through the established P8-04 runner:

- `p811.interrupted_materialisation` terminates the executor at `evidence.after_materialize_before_commit` after record insertion and before fulfilment. It proves actual transaction rollback, an open obligation, a fresh-connection retry and unchanged source truth.
- `p811.existing_assertion` proves the supported committed-record recovery input, repeated terminal replay, truthful source/materialisation/fulfilment times and the minimum envelope.
- `p811.concurrent_execution` holds the first real Audit transaction after insertion while a generated worker contends. It observes separate backend PIDs, different transaction IDs and `pg_blocking_pids`, then verifies both executions succeed with one assertion and unchanged Identity truth.
- `p811.restart_backlog` boots independent BEAM instances to reconstruct a deleted job, repeat scheduling, then recreate execution after discard and run all duplicate copies. The retained source correlation and one fulfilled assertion survive those process boundaries. It invokes the real generated scheduler/worker directly under Oban manual testing; it does not claim a wall-clock cron scheduling test.

The [callbacks](../../test/support/proof/p8_11.ex), [TEST-only checkpoint](../../test/support/proof/audit_seam.ex) and [restart script](../../test/proof/p8_11_restart.exs) use real PostgreSQL and existing Scenario/CutPoints machinery. Production compilation removes checkpoint calls. [The catalogue](../../test/support/proof/catalog.ex) retains the earlier P8-05 E2 acceptance proofs and all other families. Scope remains partial, so these cases cannot produce a full TB-001 PASS.
