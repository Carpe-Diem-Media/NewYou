## 2. Architecture, sequence and ownership

1. [RegistrationBoundary](../../lib/new_you_web/registration_boundary.ex) dispatches `/login/magic` and `/login/magic/confirm` without full-connection router telemetry. GET and HEAD display forms only. [MagicLoginController](../../lib/new_you_web/controllers/magic_login_controller.ex) calls `Identity.request_magic_login/3` for a CSRF-protected request POST. Every eligible-format public request receives the same neutral acceptance page.
2. [Identity](../../lib/new_you/identity.ex) delegates issuance to `MagicLogin.request/3`. It canonicalizes email, finds an existing Account, locks and rereads it, and checks verification, active credentials, open state and normal security posture. The Account lock serializes issuance and consumption. Identity supersedes prior current magic proofs, creates one new Token, and calls `Communications.establish_magic_login/1` within the same PostgreSQL transaction.
3. [Communications](../../lib/new_you/communications.ex) binds the immutable EN/AF Content version and rendering snapshot to its MessageIntent. Its existing AshOban trigger schedules only the intent ID. No magic-login ProtectedEnvelope is created.
4. [Executor](../../lib/new_you/communications/executor.ex) locks its intent and asks `Identity.magic_login_delivery/3` for a current transient serialization. Identity locks Account then Token and rechecks purpose, Account binding, destination, locale and original expiry. Communications rechecks Content and provider prerequisites before admission and again at invocation fencing. Provider I/O runs after the authoritative transaction, through the existing delivery path.
5. Only explicit CSRF-protected confirmation POST calls `Identity.authenticate_magic_link/1`. Identity verifies the bearer, locks Account then Token, rechecks current authority, marks the proof consumed, and calls the shared `PasswordSession.issue_current/2`. Proof consumption, user Token issuance and Session creation commit together. The controller renews the existing encrypted cookie transport and redirects. Future access uses the existing `Identity.authorize_session/1` checks.

Identity owns Account, proof and Session truth. Content & Media owns message eligibility and exact bytes. Communications owns obligations, attempt admission and provider evidence. Delivery does not call authentication or create a Session. See the [Communications handoff](p8-10-communications-handoff.md) and [Session handoff](p8-08-password-session-handoff.md) for inherited behavior.

## 3. Ash map

[Account](../../lib/new_you/identity/account.ex) adds private generic action `:authenticate_magic_link`, with sensitive `:proof`, implemented by [AuthenticateMagicLink](../../lib/new_you/identity/actions/authenticate_magic_link.ex). The existing password framework strategy remains unchanged. [Token](../../lib/new_you/identity/token.ex) adds private create-only `:issue_magic_login` and filtered `:supersede_magic_login` / `:consume_magic_login` actions. Its framework `StoreTokenChange` decodes the transient issued JWT; Identity supplies Account ownership through `SetTokenAccount`.

[Session](../../lib/new_you/identity/session.ex) extends the existing private `:issue` action with authentication method and source-proof JTI. Resource actions remain private and deny ordinary authorization. Supported business entry points are on Identity; `MagicLogin` and `PasswordSession.issue_current/2` are internal implementations. The latter requires an already locked and eligible Account in the same Token/Session transaction.

[MessageIntent](../../lib/new_you/communications/message_intent.ex) extends its existing role, source-purpose and render-schema allowlists. No parallel delivery worker, provider state machine or business-write API is introduced. The pinned [AshAuthentication 4.15.1 and Joken 2.7.0](../../mix.lock) provide JWT validation and pure signing. `Jwt.token_for_user` upserts framework Tokens and is used only for the existing Session token issuance. Magic delivery uses `Joken.encode_and_sign` on retained fixed claims, which writes nothing. Version-matched primary implementations are [AshAuthentication Jwt](https://github.com/team-alembic/ash_authentication/blob/v4.15.1/lib/ash_authentication/jwt.ex), [Jwt.Config](https://github.com/team-alembic/ash_authentication/blob/v4.15.1/lib/ash_authentication/jwt/config.ex) and [Joken](https://github.com/joken-elixir/joken/blob/v2.7.0/lib/joken.ex).

Ash Signals was considered. A direct owning-Domain call is required here to establish the delivery obligation atomically with proof issuance; no deferred reaction replaces that result. Temporal Resources has no matching as-of/effective-period requirement. No dependency, extra service or new authority store is added.

## 4. Important interface contracts

`Identity.request_magic_login(email, locale, operation_id)` always returns `:ok`. It accepts canonicalizable email, exact `en` or `af`, and a UUID operation ID. Invalid, unknown or ineligible inputs do not register an Account. A retained request ID is never reissued. A fresh successful request commits the proof and delivery obligation together; failed Content or persistence prerequisites roll back issuance and supersession. See [MagicLogin.issue_locked/4 and issue_new/3](../../lib/new_you/identity/magic_login.ex).

The request is a standalone owner operation. [Application](../../lib/new_you/application.ex) starts a development/test-only `Task.Supervisor` with at most 32 temporary request workers. `MagicLogin.request/3` uses `async_nolink`, waits at most the remaining 250 ms work budget, and calls `Task.shutdown(..., :brutal_kill)` on overrun. Each worker also installs an unlinked OTP one-shot kill timer before starting work. That timer survives caller death and prevents an abandoned request from continuing indefinitely. Successful and failed workers cancel their timer. Workers never restart automatically and retain no business authority. Lookup, current checks, proof supersession, Token and MessageIntent writes remain one owning Ash transaction with an additional database timeout. Ash's transaction timeout alone does not interrupt arbitrary callback work, so it is insufficient for this public timing contract.

Every request outcome waits outside the transaction until the same 500 ms minimum response window, including unknown/ineligible Accounts, invalid inputs, exceptions, exits, timeouts, admission exhaustion and retained-operation retries. Padding holds no transaction lock. Killing an unfinished worker rolls its transaction back. If commit wins the cancellation race, the retained operation ID makes an unchanged retry harmless. No result from a worker authenticates an Account. This is deliberate timing treatment under the tested runtime conditions, not mathematically identical network timing or a guarantee against host/VM scheduling pauses. The 32-worker cap is a bounded development resource choice, not a production velocity/risk policy. No dependency, external service or durable queue is added. Igniter's child insertion targets the unconditional application list; the fixture-gated child function was hand-edited to preserve the development boundary. See [MagicLogin.request/3](../../lib/new_you/identity/magic_login.ex), pinned [Task.Supervisor](https://github.com/elixir-lang/elixir/blob/v1.20.5/lib/elixir/lib/task/supervisor.ex), [Task yield/shutdown](https://github.com/elixir-lang/elixir/blob/v1.20.5/lib/elixir/lib/task.ex), [OTP timer](https://www.erlang.org/doc/apps/stdlib/timer.html#kill_after/2), [Ash transaction](https://github.com/ash-project/ash/blob/v3.37.2/lib/ash.ex) and [DBConnection 2.10.2](https://db-connection.hexdocs.pm/2.10.2/DBConnection.html#transaction/3).

`Identity.magic_login_delivery(reference, destination, locale)` is a trusted Communications seam and requires an existing transaction. It returns `{:ok, transient_bearer}`, `{:error, :source_invalid}`, or `{:error, :capability_unavailable}`. Callers must never retain or log the bearer. Missing signing capability or infrastructure failure holds delivery; known invalid source closes dispatch. The fixed claims and keyed Account binding prevent key replacement from re-signing an old proof under a different key. Temporary key loss can recover the same proof with its unchanged deadline. See [MagicLogin.delivery/3 and account_binding/1](../../lib/new_you/identity/magic_login.ex).

`Identity.authenticate_magic_link(proof)` accepts a bounded binary and returns `{:ok, %{session_id: id, token: transient_session_token}}` or the single neutral `{:error, :authentication_unavailable}`. Its caller must represent explicit participant confirmation. The bearer alone does not authorize a protected business action after issuance; callers must use existing Session authorization. See [Identity](../../lib/new_you/identity.ex) and [PasswordSession](../../lib/new_you/identity/password_session.ex).

`Communications.establish_magic_login/1`, `execute/1` and `reconcile/4` are trusted owning interfaces, not public HTTP endpoints. Establishment accepts Identity provenance and binds content itself. Execution and authenticated provider reconciliation retain the existing ambiguity semantics. Provider acceptance, delivery, callback or conflicting evidence never changes Account, proof or Session authority. See [Communications](../../lib/new_you/communications.ex) and [delivery tests](../../test/new_you/communications/magic_login_delivery_test.exs).

## 5. Lifecycle, failure and recovery

A proof starts with purpose `magic_login`. New issuance changes the previous current purpose to `magic_login_superseded`. Successful explicit consumption changes it to `magic_login_consumed`. Expiry is checked against the original 15-minute deadline; framework revocation or a missing Token also denies use. A consumed, superseded, revoked or expired proof cannot be revived by rematerialization. Current Account checks also reject an unverified email, changed email or verifier, inactive credential, closure or security hold. The keyed Account binding covers the issuance state and original signing configuration. See [MagicLogin.valid_current?/2](../../lib/new_you/identity/magic_login.ex) and [lifecycle tests](../../test/new_you/identity/magic_login_lifecycle_test.exs).

The Account lock precedes Token locking for delivery and consumption. Issuance holds the same Account lock before supersession. Conditional consume action and the unique source-proof Session index provide additional enforcement. A failed Session insertion rolls back proof consumption and user Token issuance, permitting a later valid retry. A successful consume followed by lost browser response remains consumed; replay cannot create or recover another Session. New issuance is required. Separate-BEAM tests prove current delivery and consumption survive application-process restart and terminal replay remains denied. They do not prove database restore, deployment or key-rotation operations. See [P809MagicLogin](../../test/support/proof/p8_09_magic_login.ex).

The existing executor retains `unknown` provider acceptance and reconciliation requirements rather than duplicating ambiguous sends. Invalid Identity source closes dispatch; unavailable Content, key or provider capability holds it. Uninvoked admission recovery rechecks current prerequisites before reopening. Conflicting evidence retains reconciliation requirements even if signing capability is temporarily missing. A provider call admitted while authority was current cannot be recalled after a later Account/proof transition; subsequent authentication still rereads Identity and fails closed. See [Executor](../../lib/new_you/communications/executor.ex).

[MagicLoginMessage](../../lib/new_you/content/magic_login_message.ex) rechecks current routers, the WELL-97 approved packet, owner-approval evidence, promoted Product/Decision hashes and exact locale artifact bytes on each binding/use. It rejects missing evidence, symlinks, obsolete routes, changed bytes and mismatched locale/version. It never falls back to the process working directory or another language. The approved content remains development-only. Low-risk browser copy is in [MagicLoginCopy](../../lib/new_you_web/magic_login_copy.ex); the existing registry email-label key is reused. See [Content tests](../../test/new_you/content/magic_login_message_test.exs).

## 6. Persistence and consistency

The [main migration](../../priv/repo/migrations/20261107145731_p8_09_magic_login.exs) adds Token fixed claims, request UUID, sensitive keyed Account binding and locale; Session authentication method and sensitive proof JTI; and Communications role/purpose/schema constraints. [Metadata completeness](../../priv/repo/migrations/20261107150356_p8_09_metadata_completeness.exs) closes SQL NULL/UNKNOWN acceptance for incomplete magic metadata. Generated snapshots match the Resource DSL.

`tokens_one_current_magic_login_index` enforces at most one current magic purpose per Account. `tokens_magic_login_request_index` binds a retained request UUID once. `sessions_one_session_per_magic_proof_index` prevents duplicate Sessions from one source proof. `sessions_authentication_provenance` pairs password with no proof JTI, and magic login with a proof JTI. `message_intents_role_purpose_schema` permits only the two approved role/purpose/schema combinations. The existing Account foreign keys and Session-per-user-token uniqueness remain in force. No proof foreign key is added to Session history, preserving framework expired-Token cleanup.

Token is the Identity-owned purpose authority for fixed claims, not an ordinary delivery record. No signed magic bearer enters MessageIntent, ProtectedEnvelope, DeliveryAttempt, Session, Oban arguments, audit evidence, logs or telemetry. The test restart helper passes synthetic transient material through stdin and emits only fixed outcome markers. Test SQL creates failures and observes constraints; application business writes use Ash. See [privacy tests](../../test/new_you/identity/magic_login_privacy_test.exs), [browser tests](../../test/new_you_web/controllers/magic_login_controller_test.exs) and [restart helper](../../test/proof/p8_09_magic_restart.exs).

Existing password Sessions receive the `password` default. No new service or backfill is required. Down migrations remove magic metadata and provenance and cannot restore the verification-only role constraint while magic intents remain. Reversal can erase lifecycle evidence and must not be used as an automatic recovery procedure. Preserve authoritative rows and design any data-aware rollback through the owning interfaces.

## 8. Future-agent extension guide

Start at `RegistrationBoundary` and `MagicLoginController`, follow the three Identity interfaces into `MagicLogin`, then inspect Token actions, Session issuance and database constraints. Follow issuance into `Communications.establish_magic_login/1`, its MessageIntent trigger, executor admission/invocation fencing, Content validation and the synthetic provider tests. Run the focused suite and the existing proof runner cases before changing lifecycle behavior. This cold-start walkthrough was checked against the implementation SHA, including source symbols, migration names, test registrations and public failure contracts. Independent Master Gate must repeat it at the reviewed PR head.

Preserve Account-before-Token lock order, owning Ash writes, create-only proof issuance, original expiry, current content/locale checks and passive retrieval. Do not call framework JWT generation to rematerialize a delivery proof, introduce a magic ProtectedEnvelope without purpose authority, treat provider evidence as authentication, expose trusted executor/reconciliation seams as public routes, or turn Session provenance into a validity bypass. Production activation, reset, recovery and primary-email-change confirmation require their own current authority and implementation work. A covered source/config/dependency change invalidates the Assent input binding and requires fresh security review and owner acceptance before rebinding.
